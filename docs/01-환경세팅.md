# 01. 환경 세팅 — 4주차 시작 전 확인

3주차에서 사용한 **PetClinic 프로젝트 루트**에서 진행합니다. 4주차는 기존 PostgreSQL과 Named Volume을 유지하면서 PetClinic `app`과 Nginx 서비스를 Compose에 추가하는 시간입니다.

> Windows 사용자는 WSL2 Ubuntu 터미널에서, macOS 사용자는 기본 터미널에서 실행합니다.

본문 크기 실습은 두 환경에서 공통으로 사용할 수 있도록 `dd`·`tr`·`curl`을 사용합니다.

## 1. 모임 전 확인할 것

아래만 확인되면 시작할 수 있습니다.

`docker-compose.yml`은 컨테이너 자체가 아니라 **여러 컨테이너를 어떻게 함께 실행할지 적어 둔 설정 파일**이다. 파일의 `services:`에는 실행할 컨테이너, `environment:`에는 환경 변수, `ports:`에는 호스트와 컨테이너의 포트 연결, `volumes:`에는 데이터 저장 위치, `networks:`에는 컨테이너 사이 연결을 적는다. `docker compose up`을 실행하면 Compose가 이 파일을 읽어 필요한 컨테이너와 실행 환경을 한꺼번에 준비한다.

```bash
docker version
docker compose version
curl --version
command -v grep awk xargs dd tr
docker compose config
docker compose ps
```

| 확인 | 정상 기준 | 4주차에서 필요한 이유 |
| --- | --- | --- |
| Docker | `docker version`에 Client·Server 정보가 표시 | Nginx·PetClinic·PostgreSQL 컨테이너 실행 |
| Compose | 버전 표시 | 세 서비스를 한 구성으로 실행 |
| 기존 Compose | `config`, `ps`가 동작 | 3주차 DB 설정·볼륨을 이어서 사용 |
| curl | 버전 표시 | 캐시 헤더·상태 코드·502를 브라우저 없이 확인 |
| 기본 셸 도구 | 각 명령의 경로 표시 | 반복 요청·로그 필터·큰 본문 생성 |

Docker Server 연결 오류가 나면 Docker Desktop을 실행합니다. WSL2 사용자는 Docker Desktop의 **Settings → Resources → WSL Integration → Ubuntu**도 켭니다.

> `docker compose down -v`는 실행하지 않습니다. PostgreSQL Named Volume까지 지워 3주차 데이터가 사라질 수 있습니다.

설정 변경 전에는 실제로 사용하는 Compose 파일을 각각 백업한다. `docker-compose.yml` 하나만 백업하고 override나 별도 `-f` 파일을 빠뜨리면 최종 적용 구성을 복구하지 못할 수 있다.

## 2. 현재 3주차 Compose 확인

현재 프로젝트의 실제 구성은 다음과 같다.

- `docker-compose.yml`: `mysql`, `postgres` 서비스가 있고 `app`은 없다.
- `docker-compose.override.yml`: PostgreSQL Named Volume `petclinic-postgres-data`가 있다.
- PostgreSQL 사용자와 DB 이름은 모두 `petclinic`이다.
- PostgreSQL은 아직 `5432:5432`로 호스트에 공개되어 있다.

따라서 4주차에는 기존 app을 수정하는 것이 아니라 **app 서비스를 새로 만든다**. MySQL 설정은 삭제하지 않고, 실습에서 `postgres app nginx`만 지정해 MySQL을 실행하지 않는다. PostgreSQL Named Volume은 그대로 유지한다.

| 확인할 값 | 파일에서 찾을 곳 | 지금 할 일 |
| --- | --- | --- |
| DB 서비스명 | `services:` 아래의 `postgres:` | 서비스명이 실제로 `postgres`인지 메모 |
| DB 사용자·DB 이름 | PostgreSQL `environment:` | 기존 값을 메모. 4주차에도 변경하지 않음 |
| PostgreSQL Named Volume | `volumes:`와 postgres의 `volumes:` | 기존 3주차 볼륨 이름을 메모. 삭제·교체하지 않음 |
| 기존 Compose 파일 목록 | 기본 파일·override·별도 `-f` 파일 | 수정할 파일을 모두 백업 |
| 기존 DB 초기화 여부 | `\dt` 또는 owners 조회 | 3주차 테이블이 이미 생성됐는지 확인 |

이 단계에서는 Compose를 아직 수정하지 않는다. 정확한 추가·삭제 코드는 [03-실습.md](03-실습.md)의 1단계에서 한 번에 적용한다.

## 3. 지금 실행할 명령

아래 명령으로 Compose 백업·병합, 기존 DB 테이블과 PetClinic 이미지를 차례로 확인한다. PostgreSQL이 이미 실행 중이어도 `up -d postgres`는 안전하게 유지된다.

```bash
cp docker-compose.yml docker-compose.yml.before-week4
cp docker-compose.override.yml docker-compose.override.yml.before-week4
docker compose config
docker compose up -d postgres
docker compose exec postgres psql -U petclinic -d petclinic -c '\dt'
docker image inspect spring-petclinic:dockerfile >/dev/null
```

테이블 목록이 보이고 마지막 명령도 오류 없이 끝나면 준비 완료다. 이미지가 없으면 다음과 같이 JAR와 이미지를 먼저 만든다.

```bash
./gradlew bootJar
docker build -t spring-petclinic:dockerfile .
```

여기까지 끝난 뒤 03-실습의 **1. Compose에 Nginx 연결하기**로 넘어간다.

## 4. 4주차에서 사용할 네트워크 구조 확인

### 왜 네트워크를 나누는가

4주차에는 사용자가 Nginx에만 접속하고, Nginx는 app에만 요청을 전달하며, app만 PostgreSQL에 접속하게 만든다. 이를 Compose 네트워크 두 개로 구분한다.

```text
사용자 → 호스트 8080 → Nginx
                         │ proxy-net(앞단)
                         ↓
                       app:8080
                         │ db-net(뒷단)
                         ↓
                    postgres:5432
```

| 서비스 | 참여할 네트워크 | 이유 |
| --- | --- | --- |
| `nginx` | `proxy-net` | 사용자 요청을 받아 app으로 전달 |
| `app` | `proxy-net`, `db-net` | Nginx 요청을 받고 DB에 접속 |
| `postgres` | `db-net` | app의 DB 연결만 받음 |

## 5. 포트와 Nginx 이미지

Nginx만 호스트의 `8080` 포트를 사용합니다. Nginx 컨테이너 내부 포트는 `80`, app 컨테이너 내부 포트는 `8080`, PostgreSQL 내부 포트는 `5432`입니다. app과 PostgreSQL에는 `ports:`를 두지 않습니다.

```text
브라우저 → 호스트 8080 → Nginx 컨테이너 80 → app 컨테이너 8080
```

### 포트 확인

아래 명령은 **4주차 수정 전의 현재 상태**를 확인한다. 지금 `5432`가 보이는 것은 3주차 설정의 `5432:5432`가 아직 남아 있기 때문이며 오류가 아니다. MySQL이 실행 중이면 `3306`도 보일 수 있다. 03-실습 1단계에서 기존 컨테이너를 내리고 `postgres app nginx`만 실행하면 3306·5432는 사라지고 Nginx용 8080만 보여야 한다.

**Ubuntu / WSL2 Ubuntu**

```bash
sudo ss -ltnp '( sport = :3306 or sport = :8080 or sport = :5432 )'
```

명령을 나누면 다음 뜻이다.

| 부분 | 의미 |
| --- | --- |
| `sudo` | 어떤 프로세스가 포트를 사용 중인지 볼 수 있도록 관리자 권한으로 실행 |
| `ss` | 현재 컴퓨터의 소켓과 포트 사용 상태 확인 |
| `-l` | 외부 연결을 기다리는 LISTEN 상태만 표시 |
| `-t` | TCP 통신만 표시 |
| `-n` | 포트 이름 대신 `8080`, `5432` 같은 숫자로 표시 |
| `-p` | 해당 포트를 사용 중인 프로세스 정보 표시 |
| `sport = :3306` | 출발점이 되는 로컬 포트 3306을 찾음 |
| `or` | 세 조건 중 하나라도 맞으면 표시 |

즉, 이 명령은 **현재 컴퓨터에서 3306·8080·5432번 TCP 포트를 열고 연결을 기다리는 프로세스가 있는지 확인**한다. 결과가 없으면 세 포트를 사용 중인 프로세스가 없다는 뜻이다.

**macOS**

```bash
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN
sudo lsof -nP -iTCP:5432 -sTCP:LISTEN
sudo lsof -nP -iTCP:3306 -sTCP:LISTEN
```

8080번이 사용 중이면 로컬 PetClinic(`./gradlew bootRun`)을 해당 터미널에서 `Ctrl+C`로 종료한다. 4주차 최종 상태에서는 호스트 8080을 Nginx만 사용한다.

> 프로젝트 루트의 기존 `conf.d/`는 MySQL 설정 폴더다. Nginx 설정은 새 `nginx/conf.d/`에 만들며 두 폴더를 합치지 않는다.

### 같은 Wi-Fi의 외부 장치 테스트 준비

선택 실습이다. 휴대폰 또는 다른 노트북 한 대를 **노트북과 같은 Wi-Fi**에 연결한다. 핫스팟과 공유기 포트포워딩은 필요 없다.

- **WSL2**: Windows 설정에서 현재 Wi-Fi의 IPv4 주소를 확인한다. (예: `192.168.0.15`)
- **macOS**: `ipconfig getifaddr en0`으로 Wi-Fi IP를 확인한다.

Nginx 실행 후 시험 기기 브라우저에서 `http://<노트북-LAN-IP>:8080`을 연다. 예: `http://192.168.0.15:8080`.

열리지 않으면 방화벽을 확인한다. 이번 실습에서는 방화벽 전체 해제나 공유기 설정은 하지 않는다. app·PostgreSQL이 외부에 공개되지 않았는지는 휴대폰 접속이 아니라 `docker compose ps`와 `docker compose port`로 확인한다.

### Nginx 이미지 받기

```bash
docker pull nginx:stable-alpine
docker image ls nginx
```

`nginx:stable-alpine`은 작은 공식 이미지이지만, 같은 태그가 시간이 지나 다른 버전을 가리킬 수 있는 이동 태그입니다. 팀 전체가 같은 결과를 재현하려면 모임 전 사용할 정확한 태그 또는 digest를 정해 Compose의 `image:`에도 똑같이 씁니다.

## 6. 캐시 효과를 확인하기 위한 app 로그 준비

### 왜 app 로그가 필요한가

3단계에서는 같은 이미지를 반복 요청해 Nginx 캐시를 사용한다. Nginx 로그의 `MISS`는 app에서 이미지를 받아왔다는 뜻이고, `HIT`는 Nginx가 저장한 이미지를 직접 응답했다는 뜻이다.

```text
MISS → Nginx → app까지 요청 전달
HIT  → Nginx 캐시에서 응답 → app에는 전달하지 않음
```

Nginx 로그만으로도 판단할 수 있지만, Tomcat access log도 켜면 HIT 요청이 app까지 가지 않았다는 사실을 양쪽 로그로 비교할 수 있다.

### 지금 만들 폴더

프로젝트 루트에서 아래 명령만 실행한다. Tomcat은 PetClinic 안에 내장되어 Spring 코드를 HTTP 요청으로 실행하는 WAS 역할을 한다. 이 폴더에는 나중에 이 **내장 Tomcat이 받은 HTTP 요청 기록**이 저장된다.

```bash
mkdir -p logs/tomcat/access
```

app 서비스의 Tomcat 환경 변수와 `volumes:`는 실제 app을 만드는 [03-실습.md](03-실습.md)의 1단계에 포함되어 있다. 환경세팅에서는 폴더만 만든다.
