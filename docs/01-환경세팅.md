# 01. 환경 세팅 — 4주차 시작 전 확인

4주차는 새 Spring 서버를 만드는 시간이 아닙니다. 3주차에서 PostgreSQL에 연결한 PetClinic을 그대로 두고, 그 앞에 Nginx 컨테이너를 추가합니다.

따라서 모임 전에는 “현재 PetClinic·PostgreSQL이 이미 정상인지”, “Docker가 Nginx를 실행할 준비가 됐는지”, “Nginx가 사용할 80번 포트가 비어 있는지”만 확인하면 됩니다.

> 모든 명령은 **Ubuntu 터미널 또는 macOS 터미널**에서 실행합니다. Windows 사용자는 PowerShell이 아니라 WSL2 Ubuntu를 엽니다.

## 1. 필요한 프로그램

| 항목 | 왜 필요한가 | 확인 명령 |
| --- | --- | --- |
| Docker Desktop | 컨테이너를 실제로 실행하는 엔진 | `docker version` |
| Docker Compose | app·postgres·nginx를 한 구성으로 관리 | `docker compose version` |
| Git | PetClinic 또는 스터디 자료를 받은 경우에만 필요 | `git --version` |
| curl | 브라우저 대신 HTTP 상태코드·응답 헤더를 확인 | `curl --version` |

```bash
docker version
docker compose version
curl --version
```

성공 기준:

- `docker version`에 **Client와 Server** 정보가 모두 나온다.
- `docker compose version`에 버전이 나온다.
- `curl --version`에 버전이 나온다.

`docker version`에 Client만 나오고 Server 연결 오류가 나오면 Docker Desktop을 먼저 실행하고, WSL2 사용자는 Docker Desktop의 **Settings → Resources → WSL Integration → Ubuntu**가 켜져 있는지 확인합니다.

## 2. 프로젝트 폴더로 이동

3주차에 사용한 PetClinic 폴더에서 진행합니다. 아래 경로는 예시이며, 자신의 실제 폴더가 다르면 그 경로를 사용합니다.

```bash
cd ~/workspace/spring-petclinic
pwd
ls
```

성공 기준: `docker-compose.yml` 또는 `compose.yml`, `build.gradle`, `src` 같은 PetClinic 파일이 보입니다.

## 3. 3주차 구성이 정상인지 먼저 확인

Nginx를 추가하기 전에 PostgreSQL과 PetClinic 구성이 이미 정상이어야 합니다. 기존 Compose 파일을 실제로 바꾸지 않고 확인만 합니다.

```bash
docker compose config
docker compose ps
```

| 확인할 것 | 정상 기준 |
| --- | --- |
| 서비스 이름 | `postgres`가 있어야 한다. 앱 서비스 이름은 실제 파일에서 확인한다. |
| PostgreSQL 상태 | `running` 또는 healthcheck를 썼다면 `healthy` |
| 기존 포트 | 3주차에는 PostgreSQL `5432` 또는 앱 `8080`이 호스트에 열려 있을 수 있다. 4주차에서 Nginx만 열도록 바꿀 대상이다. |
| 볼륨 | PostgreSQL Named Volume이 유지되어 있어야 한다. |

`docker compose config`는 Compose 기본 파일과 `docker-compose.override.yml`을 합친 **최종 설정**을 보여 줍니다. 3주차에서 만든 override 파일이 있으면 특히 이 결과를 봐야 합니다.

> 아직 `docker compose down -v`를 실행하지 않습니다. 이 명령은 PostgreSQL Named Volume까지 지워 데이터가 사라질 수 있습니다.

## 4. Nginx 이미지 준비

모임 중 이미지 다운로드 때문에 기다리지 않도록 미리 받아 둡니다.

```bash
docker pull nginx:stable-alpine
docker image ls nginx
```

성공 기준: `nginx` 이미지와 `stable-alpine` 태그가 보입니다.

`stable-alpine`은 용량이 비교적 작은 공식 Nginx 이미지의 **현재 stable 계열을 가리키는 이동 태그**입니다. `latest`와 마찬가지로 시간이 지나면 같은 태그가 다른 이미지로 바뀔 수 있습니다. 이번 실습에서 모두 같은 결과를 재현하려면, 모임 전에 팀에서 사용할 정확한 버전 태그 또는 이미지 digest를 정해 Compose의 `image:`에도 같은 값을 씁니다. 예를 들어 `nginx:stable-alpine`을 그대로 쓸 수는 있지만, 이것을 “버전이 고정됐다”라고 보면 안 됩니다.

## 5. 포트 충돌 확인

4주차에서는 Nginx가 호스트의 80번 포트를 사용합니다. 80번이 이미 사용 중이면 Nginx 컨테이너는 시작하지 못합니다.

### Ubuntu / WSL2 Ubuntu

```bash
sudo ss -ltnp '( sport = :80 or sport = :8080 or sport = :5432 )'
```

### macOS

```bash
sudo lsof -nP -iTCP:80 -sTCP:LISTEN
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN
sudo lsof -nP -iTCP:5432 -sTCP:LISTEN
```

| 포트 | 4주차의 의미 |
| --- | --- |
| 80 | 호스트에 공개되는 Nginx 입구 |
| 8080 | PetClinic의 컨테이너 내부 포트. 4주차에는 호스트에 공개하지 않음 |
| 5432 | PostgreSQL의 컨테이너 내부 포트. 4주차에는 호스트에 공개하지 않음 |

80번이 이미 사용 중이면, 그 프로그램을 무조건 종료하지 않습니다. 어떤 프로그램인지 먼저 확인한 뒤 팀원 모두가 같은 80번을 사용할 수 있는지 결정합니다. 임시로는 `8088:80`처럼 호스트 포트만 바꿔 실습할 수 있지만, 자료의 기본 흐름은 `80:80`입니다.

## 6. 실제 파일에서 확인할 값

4주차 설정을 복사하기 전에 아래 값은 현재 프로젝트 파일에서 찾아 적습니다.

| 항목 | 확인 위치 | 예시 |
| --- | --- | --- |
| 앱 Compose 서비스명 | `docker-compose.yml`의 `services:` | `app` |
| PostgreSQL 서비스명 | 같은 위치 | `postgres` |
| PostgreSQL 사용자·DB 이름 | `environment:` | `petclinic` |
| 앱이 듣는 내부 포트 | `server.port`, Dockerfile, 이미지 문서 | `8080` |
| 앱 이미지 또는 build 설정 | `app` 서비스 | 실제 프로젝트마다 다름 |

이 자료는 설명을 위해 Nginx가 `app:8080`, PetClinic이 `postgres:5432`에 연결한다고 씁니다. 서비스명이 다르면 **Nginx 설정의 `app`만 실제 서비스명으로 바꿔야 합니다.**

## 모임 전 완료 기준

- [ ] Ubuntu 또는 macOS 터미널에서 Docker Client와 Server를 모두 확인했다.
- [ ] PetClinic 프로젝트 폴더에서 `docker compose config`를 확인했다.
- [ ] 기존 PostgreSQL 컨테이너와 Named Volume 상태를 확인했다.
- [ ] Nginx 이미지를 내려받았다.
- [ ] 80·8080·5432 포트의 사용 여부를 확인했다.
- [ ] 앱 서비스명과 PostgreSQL 사용자·DB 이름을 적어 두었다.
