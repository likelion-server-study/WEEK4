# 4주차 트러블슈팅 — Nginx·Compose에서 막혔을 때

문제가 생기면 설정을 여러 번 바꾸기 전에 **서비스 상태 → 공개된 포트 → Nginx 문법 → 서비스별 로그** 순서로 확인합니다.

```bash
docker compose ps
docker compose config
docker compose logs --tail 80 nginx
docker compose logs --tail 80 app
docker compose logs --tail 80 postgres
```

`docker compose down -v`는 컨테이너뿐 아니라 이름 있는 볼륨의 DB 데이터도 지울 수 있으므로, 아래 해결 순서에는 넣지 않습니다.

---

## 1. `Cannot connect to the Docker daemon`이 나온다

| 내용 | 확인 |
| --- | --- |
| 증상 | `docker compose ...` 실행 직후 Docker daemon에 연결할 수 없다고 나옴 |
| 원인 후보 | Docker Desktop이 꺼짐, WSL Integration이 꺼짐 |
| 확인 명령 | `docker version`, `docker info` |
| 해결 | Docker Desktop을 실행하고 Engine running을 확인한다. WSL 사용자는 Docker Desktop → Settings → Resources → WSL Integration에서 Ubuntu를 켠다. |
| 복구 확인 | Ubuntu/mac 터미널에서 Client와 Server 정보가 모두 표시되고 `docker compose ps`가 실행됨 |

Windows PowerShell에서 Docker가 되더라도 Ubuntu에서 안 될 수 있습니다. 이번 실습 명령은 **Docker Desktop과 연결된 Ubuntu 터미널 또는 macOS 터미널**에서 실행합니다.

---

## 2. `docker compose`가 현재 구성을 찾지 못한다

| 내용 | 확인 |
| --- | --- |
| 증상 | `no configuration file provided`, 서비스 이름을 찾지 못함 |
| 원인 후보 | `docker-compose.yml`이 없는 폴더에서 실행함 |
| 확인 명령 | `pwd`, `ls`, `ls docker-compose*.yml` |
| 해결 | PetClinic 프로젝트 폴더로 이동한다. 예: `cd ~/workspace/spring-petclinic` |
| 복구 확인 | `docker compose config`가 최종 YAML을 출력함 |

`docker compose`는 **명령을 입력한 폴더**의 Compose 파일을 기준으로 서비스를 찾습니다. 다른 프로젝트 폴더에서 실행하면 그 프로젝트의 컨테이너를 대상으로 하므로 주의합니다.

---

## 3. 80번 포트가 이미 사용 중이다

| 내용 | 확인 |
| --- | --- |
| 증상 | `Bind for 0.0.0.0:80 failed` 또는 Nginx 컨테이너가 바로 종료됨 |
| 원인 후보 | 다른 Nginx·웹 서버·Docker 컨테이너가 이미 호스트 80번을 사용 |
| Ubuntu/WSL 확인 | `sudo ss -ltnp '( sport = :80 )'` |
| macOS 확인 | `sudo lsof -nP -iTCP:80 -sTCP:LISTEN` |
| Docker 확인 | `docker ps --format 'table {{.Names}}\t{{.Ports}}'` |
| 해결 | 기존 프로그램을 정상 종료하거나, 이번 실습의 Nginx 호스트 포트를 `8088:80`처럼 바꾼다. |
| 복구 확인 | `docker compose ps`의 Nginx PORTS에 `0.0.0.0:80->80/tcp` 또는 `8088->80`이 보이고 해당 주소로 접속됨 |

포트를 `8088:80`으로 바꿨다면 이후 주소도 `http://localhost:8088`로 바꿉니다. `80`은 컨테이너 내부 Nginx 포트이고, `8088`은 내 컴퓨터에서 들어갈 입구입니다.

## 4. Nginx가 시작되지 않거나 `nginx -t`가 실패한다

| 내용 | 확인 |
| --- | --- |
| 증상 | `docker compose up -d` 뒤 Nginx가 `exited`, 또는 `nginx -t`가 실패 |
| 원인 후보 | YAML 들여쓰기 오류, Nginx 지시어를 잘못된 범위에 둠, 세미콜론 누락 |
| 확인 명령 | `docker compose config`, `docker compose logs --tail 100 nginx`, `docker compose run --rm --no-deps nginx nginx -t` |
| 해결 | 오류 메시지에 나온 파일·줄 번호를 고친다. `log_format`, `proxy_cache_path`, `limit_req_zone`은 `server {}` 안이 아니라 `http` 범위에 있어야 한다. |
| 복구 확인 | `nginx: configuration file ... test is successful` 뒤 `curl -i http://localhost/`가 응답함 |

### 안전한 복구 순서

설정을 시험하기 전 원본을 남깁니다.

```bash
cp nginx/conf.d/default.conf nginx/conf.d/default.conf.before-test
```

Nginx가 설정 오류로 이미 종료됐다면 `docker compose exec nginx ...`는 실행할 컨테이너가 없어 실패합니다. 이때는 `docker compose run --rm --no-deps nginx nginx -t`로 문법을 먼저 확인합니다. 문법 오류가 났다면 reload하지 말고, 원본을 되돌린 뒤 다시 검사합니다.

```bash
cp nginx/conf.d/default.conf.before-test nginx/conf.d/default.conf
docker compose run --rm --no-deps nginx nginx -t
docker compose exec nginx nginx -s reload
```

`nginx -s reload`은 **설정 파일만 다시 읽게** 합니다. Compose의 포트·볼륨·환경 변수처럼 컨테이너 구성 자체를 바꿨다면 다음처럼 Nginx 컨테이너를 재생성합니다.

```bash
docker compose up -d --force-recreate nginx
```

## 5. `http://localhost/`에서 `502 Bad Gateway`가 나온다

| 내용 | 확인 |
| --- | --- |
| 증상 | Nginx는 응답하지만 상태 코드가 `502` |
| 뜻 | Nginx 자체는 살아 있으나 뒤쪽 PetClinic에 연결하지 못함 |
| 원인 후보 | app 컨테이너가 중지됨, `proxy_pass`의 서비스명이 실제 Compose 서비스명과 다름, 앱이 아직 기동 중 |
| 확인 명령 | `docker compose ps`, `docker compose logs --tail 100 app`, `docker compose logs --tail 100 nginx` |
| 추가 확인 | `docker compose exec nginx nginx -T | grep proxy_pass` |
| 해결 | app을 `docker compose start app`으로 시작하고, 설정의 `proxy_pass http://app:8080;`에서 `app`이 실제 서비스명인지 확인한다. |
| 복구 확인 | app 로그에서 Spring 기동 완료를 확인한 뒤 `curl -i http://localhost/`가 `200` 계열 응답 |

app을 일부러 멈춰 `502`를 보는 것은 정상 실습입니다.

```bash
docker compose stop app
curl -i http://localhost/
docker compose logs --tail 80 nginx

docker compose start app
docker compose logs -f app
```

마지막 명령은 로그만 실시간으로 보는 명령입니다. 준비 완료가 보이면 `Ctrl+C`로 로그 보기만 종료하고 다시 요청합니다. 컨테이너는 멈추지 않습니다.

## 6. `localhost:8080` 또는 `localhost:5432`로 여전히 직접 접속된다

| 내용 | 확인 |
| --- | --- |
| 증상 | 4주차 구성 뒤에도 앱 또는 DB 호스트 포트가 열림 |
| 원인 후보 | 기존 `docker-compose.yml` 또는 `docker-compose.override.yml`에 `ports:`가 남음, 다른 로컬 프로그램이 해당 포트를 사용 |
| 확인 명령 | `docker compose config`, `docker compose ps`, `docker compose port app 8080`, `docker compose port postgres 5432` |
| 해결 | app·postgres의 `ports:` 항목을 제거하고 `expose:`만 둔다. override 파일도 최종 구성에 합쳐지므로 같이 확인한다. |
| 복구 확인 | `docker compose port app 8080`과 postgres 명령이 매핑 없음으로 끝나고, `docker compose ps`의 PORTS에는 Nginx만 표시됨 |

`docker compose config`는 여러 Compose 파일을 합친 **실제 적용 예정 구성**을 보여 줍니다. 파일 하나만 보고 판단하지 말고 이 결과에서 `ports:`가 남았는지 확인해야 합니다.

설정을 고친 뒤에는 컨테이너 구성이 달라졌으므로 다음을 실행합니다.

```bash
docker compose up -d --force-recreate app postgres nginx
```

그 다음에도 `localhost:8080`이 열린다면, 해당 포트를 **다른 프로그램**이 쓰는지 3번의 포트 확인 명령으로 확인합니다.

## 7. 앱이 PostgreSQL에 연결하지 못한다

| 내용 | 확인 |
| --- | --- |
| 증상 | app 로그에 connection refused, authentication failed, database 관련 오류 |
| 원인 후보 | PostgreSQL이 아직 준비되지 않음, URL의 host가 `localhost`로 남음, 사용자·비밀번호·DB 이름 불일치, `service_healthy`인데 healthcheck가 없음 |
| 확인 명령 | `docker compose ps`, `docker compose logs --tail 100 postgres`, `docker compose exec postgres pg_isready -U petclinic -d petclinic` |
| 해결 | Compose 내부에서 앱이 DB에 갈 때는 `localhost`가 아니라 `postgres:5432`를 쓴다. 3주차의 사용자·DB 이름·비밀번호와 app 환경 변수를 맞춘다. `condition: service_healthy`를 썼다면 postgres에 `pg_isready` healthcheck도 둔다. |
| 복구 확인 | `pg_isready`가 accepting connections, app 로그에서 DB 연결 후 정상 기동 |

컨테이너 안의 `localhost`는 **그 컨테이너 자신**입니다. 즉 app 컨테이너에서 `localhost:5432`는 PostgreSQL 컨테이너가 아니라 app 내부를 가리키므로 DB 연결 주소로 쓰면 안 됩니다.

## 8. 캐시에서 `HIT`가 나오지 않는다

| 내용 | 확인 |
| --- | --- |
| 증상 | 같은 정적 파일을 반복 요청해도 `X-Cache-Status: HIT`가 없음 |
| 원인 후보 | 정적 파일 경로가 캐시 location과 맞지 않음, URL이 매번 달라짐, upstream이 캐시 금지 헤더를 보냄, Nginx 설정이 reload되지 않음 |
| 확인 명령 | `curl -sS -D - -o /dev/null 'http://localhost/<정적파일>?study=1'`, `docker compose logs --tail 100 nginx` |
| 해결 | 브라우저 Network 탭에서 실제 `.css`, `.js`, `.png` 경로를 다시 고른다. 동일한 URL을 두 번 요청한다. 응답의 `Cache-Control`, `Set-Cookie`도 확인한다. |
| 복구 확인 | 첫 요청 `MISS`, 같은 URL 두 번째 요청 `HIT`; 로그에서 HIT 요청의 `upstream`/`upstream_time`이 비어 있거나 `-` |

캐시 비교는 동적 화면(`/owners` 등)이 아니라 CSS·이미지·JavaScript처럼 사용자와 DB 상태에 따라 바뀌지 않는 파일로 합니다. 동적 화면을 억지로 캐시하면 이전 사용자의 결과를 다른 사용자에게 보여 줄 위험이 있습니다.

`?study=<새 숫자>`는 **새로운 캐시 키**를 만들어 첫 요청을 다시 `MISS`로 만드는 안전한 방법입니다. 캐시 볼륨을 지울 필요가 없습니다.

## 9. 요청 제한 실습에서 `429`가 나오지 않는다

| 내용 | 확인 |
| --- | --- |
| 증상 | 동시 요청을 많이 보내도 모두 `200` |
| 원인 후보 | 요청한 경로에 `limit_req`가 적용되지 않음, `burst`가 너무 큼, 요청 수·동시성이 부족함, 설정 반영 전 |
| 확인 명령 | `docker compose exec nginx nginx -T | grep -E 'limit_req|limit_req_zone|limit_req_status'` |
| 해결 | `limit_req`가 실제 요청 location에 있는지 확인하고, 시험 중에는 `rate=5r/s`, `burst=10 nodelay`, `limit_req_status 429;`처럼 낮은 기준을 쓴다. |
| 복구 확인 | `seq 1 50 | xargs -P 20 ...` 결과에 `429`가 있고 Nginx access log에 `status=429`, `rate_limit=REJECTED`가 보임. error log에도 제한 메시지를 보려면 `error_log`가 `notice` 이상을 출력해야 함 |

`limit_req`를 `location /`에만 두고 정적 파일용 별도 `location ~* ...`을 만들면, 정적 파일 요청에는 제한이 적용되지 않을 수 있습니다. 제한을 시험할 때는 `/`처럼 해당 설정이 확실히 적용되는 경로를 요청합니다.

## 10. 본문 크기 제한·메서드 제한 결과가 예상과 다르다

| 시험 | 증상 | 먼저 확인할 것 | 기대 상태 |
| --- | --- | --- | --- |
| 큰 본문 | `413`이 안 나옴 | `client_max_body_size 1k;`가 해당 location 또는 server에 적용됐는지, 실제 본문이 1 KiB보다 큰지 | `413` |
| TRACE | `405`가 안 나옴 | 허용 메서드 제한이 요청한 location에 적용됐는지 | `405` |
| 보안 헤더 | 헤더가 없음 | `add_header ... always;`를 넣고 Nginx reload 했는지 | 응답 헤더에 표시 |

확인 명령:

```bash
# 2 KiB 본문
head -c 2048 /dev/zero | tr '\0' 'a' | \
  curl -sS -i -X POST --data-binary @- http://localhost/<본문-제한-경로>

# 읽기 전용으로 정한 경로에서만 시험
curl -sS -i -X TRACE http://localhost/<읽기-전용-경로>

# 응답 헤더
curl -sS -D - -o /dev/null http://localhost/ | \
  grep -iE '^(server|x-content-type-options|x-frame-options|referrer-policy):'
```

메서드 제한은 PetClinic 전체에 적용하면 등록·수정 기능까지 고장 낼 수 있습니다. 읽기 전용 실습 경로에 한정하거나, 확인 후 원래 설정으로 되돌립니다.

## 11. 로그가 너무 많거나 찾는 상태 코드가 안 보인다

| 하고 싶은 일 | 명령 |
| --- | --- |
| Nginx 최근 80줄 | `docker compose logs --tail 80 nginx` |
| PetClinic 최근 10분 | `docker compose logs --since 10m app` |
| Nginx만 실시간 | `docker compose logs -f nginx` |
| 캐시 상태만 | 아래 캐시 상태 명령 |
| 429·502만 | 아래 상태 코드 명령 |
| Nginx 오류만 | 아래 오류 명령 |

```bash
docker compose logs nginx --no-log-prefix | grep -E 'cache=(HIT|MISS|BYPASS)'
docker compose logs nginx --no-log-prefix | grep -E 'status=(429|502)'
docker compose logs nginx --no-log-prefix | grep -Ei 'error|connect\(\) failed|upstream'
```

access log의 `cache=HIT`는 Nginx가 응답을 끝냈다는 증거입니다. `cache=MISS`와 `upstream=...`는 PetClinic까지 요청이 전달됐다는 증거입니다. `502`는 access log의 상태와 error log의 upstream 연결 실패 메시지를 함께 봐야 원인을 분리할 수 있습니다.

## 마지막 확인 목록

```bash
docker compose ps
docker compose exec nginx nginx -t
curl -i http://localhost/
docker compose logs --tail 30 nginx
```

| 확인 | 정상 기준 |
| --- | --- |
| 서비스 상태 | nginx·app·postgres가 running, PostgreSQL은 healthcheck를 쓴다면 healthy |
| 문법 | `nginx -t` 성공 |
| 접속 | Nginx 공개 주소는 응답, app·postgres 직접 호스트 포트는 미공개 |
| 로그 | Nginx access log에서 요청·상태·캐시·upstream 정보를 확인 가능 |

참고: [Docker Compose logs](https://docs.docker.com/reference/cli/docker/compose/logs/), [Nginx proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [Nginx request limit](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)
