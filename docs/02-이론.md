# 02. 이론 — Nginx는 서버 앞에서 무엇을 하는가

## 0. 이번 구조에서 쓰는 네 가지 이름

웹 서비스 구조를 설명할 때 **웹 서버**, **웹 애플리케이션**, **WAS**, **앱 서버**라는 말이 함께 나옵니다. 이들은 모두 같은 대상을 뜻하지 않습니다.

| 이름 | 정의 | 우리 스터디에서 대응되는 것 |
| --- | --- | --- |
| 웹 서버 (Web Server) | HTTP 요청을 먼저 받고, 정적 파일을 제공하거나 뒤쪽 서버로 요청을 전달하는 서버 프로그램 | Nginx 컨테이너 |
| 웹 애플리케이션 (Web Application) | 브라우저를 통해 제공할 서비스 기능을 구현한 코드 | PetClinic의 Controller·Service·Repository 등 Spring 코드 |
| WAS (Web Application Server) | 웹 애플리케이션 코드를 HTTP 요청에 맞게 실행하도록 돕는 서버 실행 환경 | PetClinic에 내장된 Tomcat의 역할 |
| 앱 서버 (Application Server) | 운영 중인 백엔드 애플리케이션 실행 단위를 부르는 실무 표현. Spring Boot에서는 앱 코드와 내장 Tomcat이 함께 들어 있어 한 단위로 부른다. | `app` 서비스의 PetClinic 컨테이너 |

현재 우리가 만드는 구조는 아래처럼 읽습니다.

```text
Nginx 컨테이너
= 앞단 웹 서버 / 리버스 프록시
        ↓
PetClinic app 컨테이너
= Spring 웹 애플리케이션 + 내장 Tomcat(WAS 역할)
= 실무에서 흔히 "앱 서버" 또는 "백엔드 애플리케이션"이라고 부르는 실행 단위
        ↓
PostgreSQL 컨테이너
= 데이터베이스 서버
```

따라서 이번 자료에서 `app`은 **PetClinic 웹 애플리케이션과 내장 Tomcat이 함께 실행되는 앱 서버**를 뜻합니다. `PetClinic = WAS`라고 부르기보다는, “PetClinic은 웹 애플리케이션이고 내장 Tomcat이 WAS 역할을 한다”라고 이해하는 편이 정확합니다.

전통적인 Java 배포에서는 Tomcat(WAS)을 따로 설치하고 PetClinic 같은 `war` 파일을 배포했습니다. Spring Boot에서는 애플리케이션과 Tomcat을 하나의 `jar`에 포함할 수 있으므로, 현재처럼 하나의 앱 컨테이너로 실행하는 경우가 많습니다.

## 1. 이번 주의 질문

3주차까지는 사용자가 PetClinic에 직접 요청을 보냈습니다. 4주차에는 Nginx를 앞에 둬서, 사용자의 모든 요청이 먼저 Nginx를 거치게 만듭니다.

```text
사용자 → Nginx → PetClinic → PostgreSQL
```

이 구조가 필요한 이유는 앱을 실행하는 PetClinic이 모든 일을 직접 하지 않게 하기 위해서입니다. Nginx는 요청의 입구에서 다음 일을 맡습니다.

- 요청을 내부 앱으로 전달한다.
- CSS·이미지처럼 반복되는 정적 파일을 캐시로 응답한다.
- 너무 많은 요청이나 너무 큰 요청을 앱에 보내기 전에 제한한다.
- 요청이 어디까지 갔는지 로그로 남긴다.
- 앱이 멈췄을 때 사용자는 어떤 오류를 받는지 보여 준다.

## 2. 리버스 프록시란 무엇인가

프록시는 누군가를 대신해 요청을 보내는 중간자입니다.

| 구분 | 누가 대신 요청하는가 | 주로 쓰는 이유 |
| --- | --- | --- |
| 포워드 프록시 | 사용자 쪽의 프록시 | 사용자 대신 외부 인터넷에 요청 |
| 리버스 프록시 | 서버 앞의 프록시 | 사용자는 내부 서버를 모르고, 프록시만 접속 |

Nginx는 이번 실습에서 **리버스 프록시**입니다. 브라우저는 PetClinic 컨테이너를 직접 모르고 Nginx에만 접속합니다. Nginx가 내부의 PetClinic으로 다시 요청을 보냅니다.

```text
브라우저의 요청: localhost:80
        ↓
Nginx가 받음
        ↓
Nginx의 내부 요청: app:8080
        ↓
PetClinic이 응답
        ↓
Nginx가 응답을 브라우저에 전달
```

Nginx가 `app:8080`에 연결한다는 것은 Docker Compose 안에서 `app`이라는 이름을 주소처럼 쓴다는 뜻입니다. `app`은 외부 인터넷 도메인이 아니라 Compose가 만든 내부 DNS 이름입니다.

## 3. 호스트 포트와 컨테이너 내부 포트

컨테이너 안의 PetClinic은 여전히 8080 포트에서 실행됩니다. 하지만 `ports:` 설정이 없으면 내 컴퓨터의 `localhost:8080`과 연결되지 않습니다.

```text
호스트(내 컴퓨터)
  localhost:80 ── 공개됨 ──> nginx 컨테이너:80

Compose 내부 네트워크
  nginx:80 ──> app:8080
  app:8080 ──> postgres:5432
```

| 주소 | 누가 접속할 수 있는가 | 4주차에서의 목적 |
| --- | --- | --- |
| `localhost:80` | 내 브라우저, 호스트 | 사용자가 접속하는 유일한 입구 |
| `app:8080` | 같은 Compose 네트워크의 컨테이너 | Nginx가 PetClinic에 요청 전달 |
| `postgres:5432` | 같은 Compose 네트워크의 컨테이너 | PetClinic이 DB에 연결 |
| `localhost:8080` | 공개하지 않으면 아무도 직접 접근 불가 | Nginx 우회 차단 확인 |

중요한 점은 컨테이너가 꺼져서 `localhost:8080`이 안 되는 것이 아니라, **앱은 실행 중이지만 호스트 포트를 공개하지 않았기 때문에** 안 되는 것이라는 점입니다. `docker compose ps`에서 앱이 실행 중인지와 `PORTS` 열을 함께 봐야 이유를 구분할 수 있습니다.

## 4. 캐시는 무엇을 저장해야 하는가

캐시는 “같은 결과를 다시 계산하거나 다시 받아오지 않기 위해, 이전 결과를 잠시 보관하는 것”입니다.

이번 실습에서 Nginx는 PetClinic의 정적 파일을 잠시 보관합니다.

| 응답 종류 | 예시 | 캐시 여부 | 이유 |
| --- | --- | --- | --- |
| 정적 파일 | CSS, 이미지, JavaScript | 가능 | 사용자마다 내용이 거의 같고 자주 바뀌지 않음 |
| 동적 화면 | 소유자 목록, 반려동물 상세, 등록·수정 결과 | 기본적으로 하지 않음 | DB 데이터·사용자 상태에 따라 내용이 바뀔 수 있음 |
| 로그인·개인 정보 | 세션, 쿠키, 사용자별 응답 | 하지 않음 | 다른 사용자에게 잘못된 내용이 보일 위험 |

캐시 요청은 다음 상태로 관찰합니다.

| 상태 | 의미 | PetClinic까지 요청이 가는가 |
| --- | --- | --- |
| `BYPASS` | 실습용으로 캐시를 일부러 우회 | 감 |
| `MISS` | 캐시에 없어서 처음 가져옴 | 감 |
| `HIT` | 캐시에 있어 Nginx가 바로 응답 | 가지 않음 |

따라서 캐시 효과는 단순히 “조금 빨라졌다”보다, **같은 파일의 요청이 앱까지 전달되는 횟수가 줄었다**는 점에서 확실히 확인할 수 있습니다.

## 5. 로그는 요청의 이동 경로를 보여 준다

이번 Nginx access log에는 다음 정보를 남깁니다.

| 로그 항목 | 의미 |
| --- | --- |
| `status` | 최종 HTTP 상태코드. 예: 200, 429, 502 |
| `request_uri` | 사용자가 요청한 경로 |
| `cache` | BYPASS, MISS, HIT 등 캐시 상태 |
| `request_time` | 사용자가 Nginx에 요청한 뒤 응답을 받을 때까지의 전체 시간 |
| `upstream_time` | PetClinic에 실제로 요청을 보낸 경우의 응답 시간 |
| `upstream` | Nginx가 요청을 전달한 뒤쪽 주소 |
| `rate_limit` | 요청 제한 결과. 예: PASSED, REJECTED |

예를 들어 `cache=HIT`이면 Nginx에서 응답이 끝났다고 볼 수 있고, `cache=MISS upstream=...`이면 PetClinic까지 요청이 갔다는 뜻입니다.

## 6. 앞단에서 제한하는 이유

PetClinic도 요청을 처리할 수 있지만, Nginx는 앱보다 앞에 있으므로 문제가 되는 요청을 앱에 보내기 전에 줄일 수 있습니다.

| 설정 | 막는 문제 | 확인할 결과 |
| --- | --- | --- |
| 요청 속도 제한 | 한 사용자가 짧은 시간에 너무 많은 요청 | `429 Too Many Requests` |
| 요청 본문 크기 제한 | 너무 큰 업로드·본문 요청 | `413 Request Entity Too Large` |
| HTTP 메서드 제한 | 읽기 전용 경로에 POST·TRACE 등이 들어옴 | `405 Method Not Allowed` |
| `server_tokens off` | Nginx 세부 버전 노출 | `Server: nginx`는 남을 수 있지만 버전 번호는 숨김 |
| 보안 응답 헤더 | 브라우저가 응답을 안전하지 않게 해석할 가능성 | 응답에 `X-Content-Type-Options` 등 추가 |

요청 속도 제한의 기본 거부 상태는 Nginx에서 `503`일 수 있습니다. 이번 스터디는 “너무 많은 요청”이라는 의미를 분명히 하기 위해 `limit_req_status 429;`를 명시합니다.

## 7. 502는 무엇을 뜻하는가

Nginx가 실행 중이고 사용자의 요청도 받았지만, 뒤쪽 PetClinic에 연결하지 못하면 Nginx는 보통 `502 Bad Gateway`를 돌려줍니다.

```text
브라우저 → Nginx: 정상
Nginx → PetClinic: 연결 실패
브라우저 ← Nginx: 502 Bad Gateway
```

4주차에서는 PetClinic이 한 대뿐이므로 앱이 멈추면 `502`가 정상적인 관찰 결과입니다. 다른 앱으로 요청을 자동 전환하는 로드밸런싱·장애 우회는 5주차에서 다룹니다.

## 8. 설정 반영: reload와 재생성

| 방법 | 언제 쓰는가 | 의미 |
| --- | --- | --- |
| `nginx -t` | 적용 전 | 설정 문법을 검사. 실패하면 적용하지 않음 |
| `nginx -s reload` | Nginx 설정 파일만 바뀜 | 실행 중인 Nginx가 설정을 다시 읽음 |
| `docker compose up -d --force-recreate nginx` | 포트·볼륨·환경 변수·이미지 등 컨테이너 구성이 바뀜 | 기존 Nginx 컨테이너를 새 설정으로 교체 |

설정을 바꾼 뒤에는 무조건 reload부터 하는 것이 아니라, 먼저 `nginx -t`가 성공해야 합니다. 잘못된 설정을 실험할 때는 원본 파일을 복사해 두고 되돌릴 수 있어야 합니다.
