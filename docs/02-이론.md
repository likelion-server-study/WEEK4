## 사전 지식. 웹 서버·웹 애플리케이션·WAS의 역할

| 이름 | 이번 스터디에서의 대상 |
| --- | --- |
| 웹 서버·리버스 프록시 | Nginx 컨테이너. 사용자 요청을 먼저 받고 `app`으로 전달한다. |
| 웹 애플리케이션 | PetClinic의 Spring 코드. 실제 서비스 기능을 처리한다. |
| WAS 역할 | PetClinic 안의 내장 Tomcat. Spring 코드를 HTTP 요청으로 실행한다. |
| 앱 서버 | 웹 애플리케이션과 내장 Tomcat이 함께 실행되는 `app` 컨테이너를 부르는 실무 표현이다. |
| DB 서버 | PostgreSQL 컨테이너. 데이터를 저장한다. |

따라서 이번 구조는 **Nginx(웹 서버) → PetClinic 앱 서버 → PostgreSQL(DB 서버)**다. PetClinic 자체는 웹 애플리케이션이고, 그 안의 내장 Tomcat이 WAS 역할을 한다.

## 0. 실습 공통: 요청이 어디까지 갔는지 로그로 확인하기

이번 실습은 응답 화면만 보고 끝내지 않고, 요청이 어디까지 전달됐는지 로그로 확인한다. 따라서 각 단계를 시작하기 전에 로그에서 사용할 항목을 먼저 알아둔다.

| 로그 필드 | 사용하는 단계 | 확인하는 것 |
| --- | --- | --- |
| `status`, `uri` | 1~5단계 | 어떤 요청이 어떤 상태 코드로 끝났는지 |
| `cache` | 3단계 | 캐시가 `BYPASS·MISS·HIT` 중 무엇이었는지 |
| `request_time`, `upstream_time` | 2·3·5단계 | 전체 처리 시간과 app 응답 시간 |
| `upstream` | 2·3·5단계 | 요청이 app까지 전달됐는지 |
| `rate_limit` | 4단계 | 요청 제한을 통과했는지 거절됐는지 |

두 파일은 모두 **Nginx 설정 파일**이며 역할이 다르다.

| 파일 | 역할 |
| --- | --- |
| `nginx/conf.d/00-observability.conf` | 여러 경로에서 공통으로 사용할 로그 형식과 캐시·요청 제한 영역을 정의하는 보조 설정 파일 |
| `nginx/conf.d/default.conf` | Nginx 컨테이너의 80번 포트에서 요청을 받고 app으로 전달하는 실제 웹 서버 설정 파일 |

`00-observability.conf`에는 로그 한 줄에 어떤 값을 남길지 다음과 같이 정의한다. `study`는 이 로그 형식에 붙인 이름이다.

```nginx
log_format study 'time=$time_iso8601 status=$status method=$request_method '
                 'uri="$request_uri" cache=$upstream_cache_status '
                 'rate_limit=$limit_req_status request_time=$request_time '
                 'upstream_time=$upstream_response_time upstream="$upstream_addr"';
error_log /dev/stderr notice;
```

`default.conf`의 `server {}` 안에서는 위에서 만든 `study` 형식을 실제 접근 로그에 사용한다.

```nginx
access_log /dev/stdout study;
```

`/dev/stdout`과 `/dev/stderr`로 보낸 로그는 `docker compose logs nginx`에서 확인할 수 있다. 파일을 만드는 위치와 전체 작성 순서는 실습 1단계에서 다룬다.

Nginx access log는 사용자의 요청을 Nginx가 어떻게 처리했는지 보여 준다. Tomcat access log는 그 요청이 PetClinic까지 도착했는지 보여 준다. 두 로그를 비교하면 다음처럼 판단할 수 있다.

```text
Nginx 로그 있음 + Tomcat 로그 있음 → app까지 전달됨
Nginx 로그 있음 + Tomcat 로그 없음 → Nginx에서 캐시 응답·차단·직접 응답했는지 확인
```

Tomcat 로그에 요청이 없다면 **그 요청이 app까지 전달되지 않았다는 뜻**이다. 다만 전달되지 않은 이유는 여러 가지일 수 있으므로 Nginx 로그를 함께 본다.

- `cache=HIT`: Nginx 캐시가 응답함
- `status=403·405·413·429`: Nginx가 요청을 차단함
- `upstream`이 비어 있음: Nginx가 app에 요청을 보내지 않고 직접 처리함

즉, Nginx 로그는 처리 결과와 이유를 확인하고 Tomcat 로그는 app 도달 여부를 확인하는 용도로 나누어 사용한다.

## 1. Compose에 Nginx·app을 추가해 함께 실행하기

지금까지는 PostgreSQL만 Compose로 실행하고 PetClinic은 따로 실행했다. 이번에는 PetClinic과 Nginx도 Compose 서비스로 등록해 세 프로그램을 함께 실행한다.

### 1-1. Compose 파일에서 바뀌는 위치

Compose 파일은 여러 컨테이너의 이미지·환경 변수·포트·볼륨·네트워크를 한곳에 적는 실행 설정이다. 실습 코드를 보기 전에 **어느 부분을 바꾸는지** 먼저 정리하면 다음과 같다.

| 파일과 위치 | 4주차에서 하는 변경 |
| --- | --- |
| `docker-compose.yml`의 `services.postgres` | 호스트에 공개하던 `ports`를 빼고, 내부 포트·DB 네트워크·준비 상태 검사를 추가한다. |
| `docker-compose.yml`의 `services.app` | 존재하지 않으므로 새로 추가한다. PetClinic 이미지, DB 주소, Tomcat 요청 로그, 네트워크를 설정한다. |
| `docker-compose.yml`의 `services.nginx` | 새로 추가한다. Nginx만 `8080:80`으로 호스트에 공개하고 app과 연결한다. |
| `docker-compose.yml` 맨 아래의 최상위 `networks`·`volumes` | `proxy-net`, `db-net`, `nginx-cache`를 선언한다. 같은 최상위 키가 이미 있으면 그 아래에 항목만 추가한다. |
| `docker-compose.override.yml` | 기존 `petclinic-postgres-data` Named Volume을 그대로 둔다. |
| `nginx/conf.d/*.conf` | 다음 절부터 리버스 프록시·캐시·로그·요청 제한을 설정한다. |

기존 `mysql` 서비스는 삭제하지 않는다. 4주차 실행 명령에서 `postgres app nginx`만 지정해 MySQL을 실행하지 않는다.

```bash
docker compose up -d postgres app nginx
```

따라서 Compose 파일에는 MySQL 설정이 남아 있어도, 이번에 실행되는 컨테이너는 PostgreSQL·app·Nginx 세 개다.

### 1-2. 기존 PostgreSQL 데이터를 다시 초기화하지 않기

3주차 DB에 이미 테이블과 데이터가 있다면 app에 `SPRING_SQL_INIT_MODE=never`를 넣는다. 앱이 시작될 때 테이블 생성 SQL을 다시 실행하지 않게 하는 설정이다. 같은 테이블이나 인덱스를 다시 만들려고 하면 `already exists` 오류로 앱 시작이 실패할 수 있기 때문이다.

빈 DB를 처음 만드는 경우에는 이 설정을 먼저 사용하면 안 된다. 테이블을 한 번 만든 뒤 기존 DB를 이어 쓸 때 적용한다.

### 1-3. DB 컨테이너가 아니라 ‘DB 준비 완료’를 기다리기

컨테이너가 실행됐다는 사실과 PostgreSQL이 접속을 받을 준비가 됐다는 사실은 다르다.

```text
PostgreSQL 컨테이너 시작
        ↓ 아직 초기화 중일 수 있음
pg_isready가 접속 가능 여부 확인
        ↓ 준비 완료
PetClinic app 시작
```

- PostgreSQL의 `healthcheck`에서 `pg_isready`를 실행해 DB가 연결을 받을 수 있는지 반복 확인한다.
- app의 `depends_on`에 `condition: service_healthy`를 두어 PostgreSQL이 준비 완료 상태가 된 뒤 app을 시작한다.

단순히 `depends_on: [postgres]`만 쓰면 PostgreSQL 컨테이너를 먼저 **시작**해 줄 뿐, DB 준비가 끝날 때까지 기다려 주지는 않는다. 실습에서는 `services.postgres.healthcheck`와 `services.app.depends_on` 두 위치를 함께 수정한다.

Docker Compose는 `condition: service_healthy`로 지정한 의존 서비스의 healthcheck가 성공할 때까지 기다린다. [Docker Compose 시작 순서 공식 문서](https://docs.docker.com/compose/how-tos/startup-order/)

### 1-4. 두 내부 네트워크를 Compose 어디에 적는가

Nginx가 DB에 직접 연결되지 않도록 통신 관계를 두 네트워크로 나눈다.

```text
nginx ── proxy-net ── app ── db-net ── postgres
```

Compose에서는 두 군데에 적는다.

1. `docker-compose.yml` 맨 아래 최상위 `networks:`에 `proxy-net`, `db-net`을 만든다.
2. 각 `services.<서비스명>.networks`에 그 서비스가 사용할 네트워크 이름을 적는다.

| 서비스 | 연결할 네트워크 | 이유 |
| --- | --- | --- |
| `nginx` | `proxy-net` | app에 HTTP 요청 전달 |
| `app` | `proxy-net`, `db-net` | Nginx 요청을 받고 PostgreSQL에 연결 |
| `postgres` | `db-net` | app의 DB 연결을 받음 |

`db-net`에는 `internal: true`를 설정해 Docker 내부 통신용으로 사용한다. 실제 YAML 조각과 들여쓰기 위치는 실습 1단계에서 그대로 작성한다.

### 1-5. 실행 직후 로그를 확인하는 이유

Compose가 컨테이너를 `running`으로 표시해도 프로그램 준비가 끝났다고 단정할 수 없다. 그래서 처음 세 서비스를 올린 직후에만 다음 로그를 확인한다.

| 확인 대상 | 확인하는 내용 |
| --- | --- |
| PostgreSQL | DB가 연결을 받을 준비가 되었는가 |
| PetClinic | `Started ...`가 출력되어 Spring 실행이 끝났는가 |
| Nginx | 브라우저나 `curl` 요청을 실제로 받았는가 |

이때 `logs --tail 30`은 마지막 30줄만 보고, `logs -f`는 준비 완료 메시지가 나올 때까지 새 로그를 따라가는 데 사용한다. 캐시·차단·장애 로그 분석은 각각의 뒤 단계에서 별도로 설명한다.

수정 전에는 Compose 파일을 백업한다. `docker compose config`로 기본 파일과 override가 합쳐진 최종 서비스·네트워크·볼륨도 확인한다.

### 1-6. 수정한 설정을 실행 중인 서버에 반영하기

설정 파일을 저장했다고 실행 중인 Nginx와 컨테이너가 항상 자동으로 바뀌는 것은 아니다. **무슨 파일을 수정했는지**에 따라 반영 방법을 선택한다.

| 방법 | 의미 | 언제 쓰는가 |
| --- | --- | --- |
| `nginx -t` | 문법 오류가 없는지 검사한다. | Nginx 설정을 바꾼 뒤, 적용하기 전에 사용한다. |
| `nginx -s reload` | 컨테이너는 유지하고 Nginx가 설정만 다시 읽게 한다. | `nginx/conf.d/*.conf`만 바뀌었을 때 사용한다. |
| `docker compose up -d --force-recreate nginx` | 기존 컨테이너를 새 Compose 설정으로 다시 만든다. | Compose의 포트·볼륨·이미지 등이 바뀌었을 때 사용한다. |

```text
nginx/conf.d 파일 수정
→ nginx -t 성공 확인
→ Nginx reload

docker-compose.yml 수정
→ docker compose config 확인
→ 영향받는 컨테이너 재생성
```

정리하면 Nginx의 요청 전달·캐시·차단 규칙만 바꿨다면 `reload`, 컨테이너의 포트·볼륨·이미지를 바꿨다면 `재생성`한다. 실제 명령과 실행 순서는 실습의 해당 단계에서 제시한다.

## 2. app·PostgreSQL은 감추고 Nginx만 공개하기

사용자가 PetClinic이나 PostgreSQL에 직접 들어가지 못하게 하고, Nginx만 공통 입구로 사용한다.

```text
브라우저 localhost:8080 → 호스트 8080 → Nginx:80 → app:8080 → postgres:5432
```

### 2-1. 공개하는 주소와 내부에서만 쓰는 주소

| 주소 | 사용하는 주체 | 목적 |
| --- | --- | --- |
| `localhost:8080` | 브라우저·curl | 호스트에 공개된 Nginx 입구 |
| `app:8080` | Nginx 컨테이너 | PetClinic으로 요청 전달 |
| `postgres:5432` | app 컨테이너 | PostgreSQL 연결 |

Nginx의 `ports: ["8080:80"]`은 호스트 8080을 Nginx 컨테이너 80에 연결하는 **포트 매핑**이다.

```text
호스트의 8080  ── Docker가 전달 ──>  Nginx 컨테이너의 80
```

app과 PostgreSQL에는 `ports:`를 두지 않는다. 따라서 호스트에서 직접 들어가는 입구는 없지만, Compose 내부에서는 계속 `app:8080`, `postgres:5432`로 연결할 수 있다. 이 두 주소는 포트 매핑이 아니라 컨테이너끼리 사용하는 내부 주소다.

### 2-2. Nginx가 app으로 요청을 전달하는 설정

`nginx/conf.d/default.conf`의 `location /`에 다음 설정을 넣는다.

```nginx
location / {
  proxy_pass http://app:8080;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

- `proxy_pass http://app:8080`: Nginx가 받은 요청을 PetClinic 컨테이너로 전달한다.
- `proxy_set_header`: PetClinic이 원래 요청 주소·사용자 IP·HTTP 또는 HTTPS 여부를 알 수 있도록 요청 정보를 함께 전달한다. 이 설정이 없으면 PetClinic에는 사용자가 아니라 바로 앞의 Nginx 정보만 보일 수 있다.

### 2-3. app·PostgreSQL이 비공개인지 확인하는 방법

이번 구성에서 `localhost:8080`은 Nginx에 연결된다. 따라서 이 주소가 열리면 **Nginx를 통한 접속 성공**을 확인한 것이지, app에 직접 접속한 것이 아니다.

app이 비공개라는 사실은 다음 두 결과를 함께 보고 판단한다.

1. `docker compose ps`에서 app이 실행 중이다.
2. `docker compose port app 8080`에는 호스트 연결 주소가 나오지 않는다.

즉, app은 실행 중이지만 호스트에서 app으로 바로 들어가는 입구가 없는 상태다. PostgreSQL도 `docker compose port postgres 5432`에 연결 주소가 나오지 않으면 같은 의미다.

### 2-4. 휴대폰에서 확인하는 것은 무엇인가

선택 실습으로, 같은 Wi-Fi의 휴대폰에서 `http://<노트북-LAN-IP>:8080`을 연다. 이것은 **다른 기기에서도 Nginx 입구로 접속할 수 있는지** 확인하는 시험이다.

휴대폰 역시 호스트 8080에 연결하므로 도착하는 대상은 Nginx다. 이 시험만으로 app이 비공개라는 사실을 증명하지는 않는다. app·PostgreSQL 비공개 여부는 앞에서 설명한 `docker compose port` 결과로 확인한다.

Nginx 로그와 Tomcat 로그에 같은 요청이 남으면 `휴대폰 → Nginx → app`으로 전달된 것도 확인할 수 있다.

## 3. 정적 파일 캐시 효과 비교하기

캐시는 이전 응답을 잠시 보관해 같은 결과를 다시 받아오는 일을 줄인다. 이번 실습에서는 CSS·이미지·JavaScript 같은 정적 파일만 캐시하고, DB 결과나 사용자 상태에 따라 달라지는 화면·폼·개인 정보 응답은 캐시하지 않는다.

### 3-1. 실제 캐시 대상 이미지 확인

이번 실습에서 사용하는 PetClinic 소스에는 다음 이미지가 들어 있다.

```text
src/main/resources/static/resources/images/pets.png
```

Spring Boot는 `src/main/resources/static` 아래의 파일을 웹의 `/` 아래로 제공한다. 따라서 소스 파일과 실행 중 요청 주소는 다음처럼 대응된다.

```text
소스 파일: src/main/resources/static/resources/images/pets.png
요청 주소: http://localhost:8080/resources/images/pets.png
```

프로젝트 루트에서 파일 존재 여부를 확인하려면 다음 명령을 사용한다.

```bash
find src/main/resources -type f -name 'pets.png'
```

실습에서는 브라우저로 실제 이미지가 보이는지 확인하고, `curl` 응답의 `Content-Type`과 파일 크기도 확인한다.

[Spring Boot 정적 파일 제공 공식 문서](https://docs.spring.io/spring-boot/reference/web/servlet.html#web.servlet.spring-mvc.static-content)

### 3-2. MISS·HIT·BYPASS의 차이

| 상태 | 의미 | PetClinic 전달 |
| --- | --- | --- |
| `BYPASS` | 비교를 위해 캐시를 우회 | 전달됨 |
| `MISS` | 캐시에 없어 PetClinic에서 가져옴 | 전달됨 |
| `HIT` | Nginx 캐시에서 바로 응답 | 전달되지 않음 |

`00-observability.conf`의 `proxy_cache_path`는 캐시 저장 영역을 만들고, 정적 파일 `location`의 `proxy_cache`가 실제 사용 여부를 정한다. 동적 `location /`에는 캐시를 적용하지 않는다.

### 3-3. 캐시 효과를 세 가지로 확인하는 이유

캐시 효과는 한 가지 수치만으로 판단하기 어렵기 때문에 다음 세 가지를 함께 확인한다.

| 확인 방법 | 무엇을 알 수 있는가 | 왜 필요한가 |
| --- | --- | --- |
| `curl -w`의 단일 요청 시간 | 사용자가 요청 한 번을 보냈을 때 얼마나 빨리 응답하는지 | MISS와 HIT의 기본적인 응답 시간 차이를 직접 확인한다. |
| 반복·동시 요청의 전체 시간 | 요청이 많을 때 전체 처리 시간과 처리량이 어떻게 달라지는지 | 로컬에서는 한 번의 요청이 너무 빨라 차이가 작으므로, 요청을 여러 번 보내 차이를 크게 관찰한다. |
| Nginx upstream과 Tomcat access log의 app 전달 횟수 | Nginx가 캐시에서 응답했는지, PetClinic까지 요청이 갔는지 | 시간은 컴퓨터 상태에 따라 달라질 수 있다. 로그를 함께 봐야 빨라진 이유가 실제 캐시 때문인지 확인할 수 있다. |

로컬의 단일 이미지 요청은 네트워크 지연이 거의 없어 차이가 작을 수 있다. 그래서 단일 요청 시간과 함께 같은 실제 이미지를 순차로 수백 번 요청한 누적 시간을 비교한다. 동시 요청은 처리량 비교에는 유용하지만 실행 순서가 섞이므로, 사람이 체감할 누적 시간 비교는 `-P 1`, 부하 상황 비교는 `-P 20`처럼 목적을 나눈다.

시간만으로 결론 내리지 않고 `X-Cache-Status`, Nginx의 `cache`·`upstream`, Tomcat 로그 줄 수를 함께 본다. Tomcat은 PetClinic에 내장되어 Spring 웹 애플리케이션을 HTTP 요청으로 실행하는 WAS 역할을 한다. PetClinic 기본 애플리케이션 로그는 모든 HTTP 요청을 한 줄씩 남긴다고 보장하지 않으므로, Tomcat access log를 별도로 켜서 실제로 app까지 도달한 요청을 센다.

## 4. Nginx 앞단에서 요청 제한·보호하기

PetClinic도 요청을 검사할 수 있지만, Nginx에서 먼저 거절하면 불필요한 요청이 app 프로세스까지 도달하지 않는다.

실습 4단계에는 아래 기능이 모두 설정과 시험 명령으로 들어 있다.

| 기능 | 실습에서 보내는 요청 | 기대 결과 | 성공 판정 |
| --- | --- | --- | --- |
| 요청 속도 제한 | 같은 주소로 병렬 요청 50회 | 일부 `429` | Nginx 로그에 `rate_limit=REJECTED`, app 전달 횟수는 전체 요청보다 적음 |
| 요청 본문 크기 제한 | `/owners/new`에 2 KiB 본문 전송 | `413` | Nginx 로그에는 413, Tomcat 로그에는 같은 `study` 요청 없음 |
| 메서드 제한 | `POST /study/read-only` | `405` | Nginx 로그에는 405, Tomcat 로그에는 같은 요청 없음 |
| 경로 접근 차단 | `GET /study/private` | `403` | Nginx 로그에는 403, Tomcat 로그에는 같은 요청 없음 |
| Nginx 버전 숨김 | 일반 응답의 `Server` 헤더 확인 | `nginx/1.x.x` 같은 버전 번호 없음 | 응답 헤더에서 확인 |
| 기본 보안 헤더 | 일반 화면과 캐시 대상 이미지 요청 | 지정한 헤더 존재 | 두 응답의 헤더를 각각 확인 |

### 4-1. 요청 속도 제한과 429

`limit_req_zone`은 클라이언트별 요청 횟수를 기억할 공간과 허용 속도를 정의하고, `limit_req`는 그 규칙을 실제 경로에 적용한다.

```nginx
# 00-observability.conf의 http 범위
limit_req_zone $binary_remote_addr zone=per_ip_rate:10m rate=5r/s;

# default.conf의 location / 안
limit_req zone=per_ip_rate burst=10 nodelay;
```

- `rate=5r/s`: IP 하나당 평균 초당 5개 요청을 허용한다.
- `burst=10`: 순간적으로 몰린 요청 10개까지 추가로 받아 준다.
- `nodelay`: 허용 범위의 요청을 기다리게 하지 않고 바로 처리한다.
- 허용 범위까지 넘으면 요청을 거절한다.

Nginx의 요청 제한 기능은 별도로 지정하지 않으면 거절된 요청에 `503 Service Unavailable`을 반환한다. 하지만 이 상황은 서버 고장보다 “요청을 너무 많이 보냈다”는 뜻에 가깝다. 그래서 `server` 범위에 다음 설정을 넣어 응답을 `429 Too Many Requests`로 바꾼다. [Nginx 요청 제한 공식 문서](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html#limit_req_status)

```nginx
limit_req_status 429;
```

`rate=5r/s`는 차단 결과를 쉽게 보기 위한 작은 학습용 값이다. 실제 서비스의 정상 요청량을 조사하지 않고 그대로 사용하면 정상 사용자도 차단될 수 있으므로, 실습이 끝나면 요청 제한 설정을 해제하거나 운영 기준에 맞는 값으로 바꾼다.

### 4-2. 본문 크기 제한과 413

`client_max_body_size`는 사용자가 보내는 요청 본문의 최대 크기다. 파일 업로드나 폼 데이터가 이 값을 넘으면 Nginx가 app으로 보내기 전에 `413 Payload Too Large`를 반환한다.

```nginx
client_max_body_size 1k;
```

실습에서는 제한이 확실히 보이도록 매우 작은 `1k`를 사용하고 2 KiB 본문을 보낸다. `1k`는 실제 PetClinic 운영값이 아니다. 확인이 끝나면 Nginx 기본값과 같은 `1m` 또는 팀이 정한 값으로 되돌린다.

### 4-3. 메서드·경로 차단

이 실습은 Nginx가 **요청의 방식이나 주소를 보고 app에 보내기 전에 거절할 수 있는지** 확인한다.

- 메서드 차단: 조회용 주소에서 `GET`은 허용하지만 데이터를 바꾸는 `POST`는 막는 방식
- 경로 차단: 관리자용·내부용 주소처럼 외부에 공개하면 안 되는 경로를 막는 방식

PetClinic의 실제 등록·수정 기능에 제한을 걸면 정상 기능이 고장 날 수 있다. 그래서 아래 두 주소는 Nginx 안에만 존재하는 **연습용 주소**로 만들며 PetClinic의 실제 기능과는 관계가 없다.

| 연습용 주소 | 보낸 요청 | Nginx의 응답 | 확인하는 기능 |
| --- | --- | --- | --- |
| `/study/read-only` | `GET` | `204 No Content` | 읽기 요청은 허용 |
| `/study/read-only` | `POST` | `405 Method Not Allowed` | 허용하지 않은 메서드 차단 |
| `/study/private` | 모든 요청 | `403 Forbidden` | 특정 경로 접근 차단 |

응답은 Nginx가 직접 만들며 app으로 전달하지 않는다. 따라서 Nginx 로그에는 `204·405·403`이 기록되고 Tomcat 로그에는 해당 요청이 없어야 한다.

### 4-4. 버전 숨김과 보안 헤더

이 부분은 요청을 차단하는 기능이 아니라 **응답에 불필요한 서버 정보를 줄이고 브라우저에 기본 보안 규칙을 알려 주는 설정**이다.

`server_tokens off`는 `nginx/1.x.x`처럼 구체적인 버전 번호를 숨긴다. Nginx를 사용한다는 사실 자체를 완전히 숨기지는 않는다.

`add_header`는 **Nginx가 브라우저로 보내는 HTTP 응답에 안내 정보를 추가하는 설정**이다. 이 헤더들은 요청을 거절하는 방화벽 기능이 아니라, 응답을 받은 브라우저가 화면과 파일을 조금 더 안전하게 처리하도록 지시한다.

| 응답 헤더 | 이번 설정 | 간단한 역할 |
| --- | --- | --- |
| `X-Content-Type-Options` | `nosniff` | CSS·이미지 등의 종류를 브라우저가 임의로 추측하지 않고, 서버가 보낸 `Content-Type`대로 처리하게 한다. |
| `X-Frame-Options` | `SAMEORIGIN` | 같은 출처의 화면만 PetClinic을 `<iframe>` 안에 넣을 수 있게 하여, 다른 사이트가 PetClinic 화면을 덮어씌우는 공격을 줄인다. |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 다른 사이트로 이동할 때 이전 페이지의 전체 주소 대신 출처 정도만 전달해 상세 경로가 불필요하게 노출되는 것을 줄인다. |

#### 왜 같은 보안 헤더를 두 곳에 적는가

일반 화면용 보안 헤더는 `server`에 설정한다. 그런데 정적 파일 `location`에는 캐시 결과를 보여 주려고 다음 헤더를 별도로 추가한다.

```nginx
add_header X-Cache-Status $upstream_cache_status;
```

Nginx는 하위 `location`에 `add_header`가 하나라도 있으면 상위 `server`의 `add_header`를 자동으로 물려주지 않는 방식으로 동작할 수 있다. 그러면 일반 화면에는 보안 헤더가 있지만 정적 이미지에는 `X-Cache-Status`만 남는 문제가 생긴다.

따라서 이번 실습에서는 다음처럼 적용한다.

```text
일반 화면 응답: server에 보안 헤더 3개 설정
정적 파일 응답: 정적 location에 X-Cache-Status와 보안 헤더 3개 설정
```

설정 후 일반 화면과 캐시 대상 이미지를 각각 요청해 두 응답 모두에 보안 헤더가 있는지 확인한다.

[Nginx add_header 상속 공식 문서](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header)

#### 왜 Nginx 로그와 Tomcat 로그를 함께 보는가

사용자 요청은 원래 `Nginx → PetClinic의 내장 Tomcat` 순서로 이동한다. Nginx가 앞에서 요청을 차단하면 다음과 같은 차이가 생긴다.

```text
Nginx access log: 차단된 요청과 429·413·405·403 상태가 기록됨
Tomcat access log: 그 차단 요청은 기록되지 않음
```

이 차이는 **Nginx가 응답을 만들었고 요청은 PetClinic까지 전달되지 않았음**을 보여 준다. 단, 요청 제한 시험에서는 허용된 요청은 Tomcat까지 전달되고 `429`로 거절된 요청만 전달되지 않는다. 실습에서는 요청 주소에 넣은 `study=...` 값을 기준으로 두 로그에서 같은 요청을 찾아 비교한다.

## 5. PetClinic 장애 확인·안내·복구

앞의 단계에서는 Nginx가 정상적인 요청을 app으로 전달했다. 이번에는 **Nginx는 살아 있지만 뒤쪽 PetClinic만 멈춘 상황**을 만든다. 이를 통해 어느 서버에서 문제가 생겼는지 로그로 구분하고, 장애 중에도 Nginx가 사용자에게 안내 화면을 보여 줄 수 있는지 확인한다.

### 5-1. PetClinic이 멈추면 왜 502가 발생하는가

```text
브라우저 → Nginx: 연결 성공
Nginx → PetClinic: 연결 실패
브라우저 ← Nginx: 502 Bad Gateway
```

`502 Bad Gateway`는 Nginx가 요청을 받았지만 전달 대상인 app에서 정상 응답을 받지 못했다는 뜻이다.

- Nginx access log의 `status=502`: 사용자가 502 응답을 받았다는 증거
- Nginx error log의 `connect() failed` 또는 upstream 오류: app 연결이 실패한 원인

### 5-2. 장애 상태는 유지하고 화면만 알기 쉽게 바꾸기

기본 Nginx 오류 화면은 사용자에게 상황을 충분히 설명하지 않는다. 그래서 다음처럼 응답을 구성한다.

```text
HTTP 상태 코드: 502 Bad Gateway
화면 내용: "현재 서비스에 연결할 수 없습니다. 잠시 후 다시 시도해 주세요."
```

브라우저에 보이는 안내 문구만 바꾸고 상태 코드는 `502`로 유지한다. 상태를 `200 OK`로 바꾸면 모니터링 프로그램이 장애를 정상 응답으로 오해할 수 있기 때문이다.

실습에서는 세 곳을 설정한다.

| 파일 | 추가하는 것 | 역할 |
| --- | --- | --- |
| `nginx/html/study-50x.html` | 사용자에게 보여 줄 짧은 안내문 | 기본 오류 화면 대신 보여 줄 내용 |
| `docker-compose.yml`의 `nginx.volumes` | `./nginx/html:/usr/share/nginx/html:ro` | 호스트의 안내 HTML을 Nginx 컨테이너에서 읽게 함 |
| `nginx/conf.d/default.conf` | `error_page`, 오류 페이지용 `location`, `proxy_intercept_errors` | 5xx 오류가 나면 안내 HTML을 사용하도록 연결 |

오류 페이지용 `location`의 `internal`은 사용자가 안내 HTML 주소를 직접 여는 것은 막고, 실제 오류 처리 중에만 Nginx가 사용하도록 한다. `proxy_intercept_errors on;`은 app이 반환한 5xx 응답도 같은 안내 화면으로 처리할 때 사용한다. [Nginx error_page·internal](https://nginx.org/en/docs/http/ngx_http_core_module.html#error_page), [Nginx proxy_intercept_errors](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_intercept_errors)

### 5-3. app 재시작과 복구 판정

app을 다시 시작한 뒤 다음 세 가지를 확인해야 복구된 것이다.

1. app 로그에 Spring의 `Started ...`가 표시된다.
2. 같은 요청이 다시 `200 OK`를 반환한다.
3. Nginx access log의 `upstream`에 app 주소가 다시 기록된다.

기존 3주차 DB를 이어 쓰는 구성에서는 app 재시작 때 초기화 SQL이 다시 실행되지 않도록 `SPRING_SQL_INIT_MODE=never`를 사용한다. 이 설정의 전제와 위치는 1단계에서 설명한다.

이번 주차에는 PetClinic 한 대를 다시 시작해 복구하는 데까지만 다룬다. 다른 app으로 자동 우회하는 로드밸런싱은 5주차 범위다.

## 참고: Docker를 사용하지 않는 회사 환경의 연결 방식

Docker를 사용하지 않아도 Nginx·앱·DB는 **IP 주소와 포트**로 서로 연결한다. 설치 위치에 따라 사용하는 주소가 달라진다.

### 한 서버에 모두 설치한 경우

세 프로그램을 같은 서버 OS에서 프로세스로 실행한다면 서버 자기 자신을 뜻하는 `127.0.0.1`을 사용할 수 있다.

```text
사용자 → 서버 공개 주소:80 → Nginx
                              ↓ 127.0.0.1:8080
                            PetClinic
                              ↓ 127.0.0.1:5432
                            PostgreSQL
```

```nginx
# 같은 서버에서 실행 중인 PetClinic으로 전달
proxy_pass http://127.0.0.1:8080;
```

```properties
# 같은 서버에서 실행 중인 PostgreSQL로 연결
spring.datasource.url=jdbc:postgresql://127.0.0.1:5432/petclinic
```

앱의 8080과 DB의 5432를 `127.0.0.1`에서만 받게 설정하면 그 서버 내부 프로세스만 연결할 수 있고, 사용자는 외부에 공개된 Nginx로 접속한다.

### Nginx·앱·DB가 서로 다른 서버인 경우

규모가 있는 회사나 클라우드 환경에서는 각 프로그램을 다른 서버에 둘 수 있다. 이때는 회사 내부망의 사설 IP나 내부 DNS 이름과 포트를 사용한다.

```text
Nginx 서버 → 10.0.1.10:8080 또는 app.internal:8080
앱 서버    → 10.0.2.20:5432 또는 db.internal:5432
```

방화벽이나 클라우드 보안 규칙도 함께 설정한다.

- 앱의 8080: Nginx 서버에서 오는 연결만 허용
- DB의 5432: 앱 서버에서 오는 연결만 허용
- 외부 사용자: Nginx의 80·443만 접근 허용

회사가 관리형 DB를 사용한다면 `db.internal` 대신 클라우드가 제공한 DB 접속 주소를 사용한다. 어떤 형태든 연결의 기본 단위는 **대상 IP 또는 DNS 이름 + 포트**다.

| 환경 | Nginx가 app에 연결 | app이 DB에 연결 |
| --- | --- | --- |
| 이번 Docker Compose 실습 | `app:8080` | `postgres:5432` |
| 한 서버에 직접 설치 | `127.0.0.1:8080` | `127.0.0.1:5432` |
| 여러 회사 서버·클라우드 | 앱의 사설 IP·내부 DNS + 8080 | DB의 사설 IP·내부 DNS + 5432 |
