# 03. 실습 — Nginx 앞단, 캐시, 로그, 요청 제한

## 실습 전 약속

- 명령은 PetClinic 프로젝트 폴더에서 Ubuntu 또는 macOS 터미널로 실행합니다.
- 이 문서는 PetClinic 내부 포트를 `8080`, PostgreSQL 서비스명을 `postgres`, DB 이름·사용자·비밀번호를 `petclinic`으로 예시를 듭니다.
- 실제 값이 다르면 [01-환경세팅.md](01-환경세팅.md)에서 확인한 값으로 바꿉니다.
- 기본 흐름에서 `docker compose down -v`는 실행하지 않습니다. DB Named Volume까지 지워질 수 있습니다.

## 1. 현재 구성 확인과 원본 백업

```bash
cd ~/workspace/spring-petclinic
docker compose config
docker compose ps
cp docker-compose.yml docker-compose.yml.before-week4
```

`cp`는 Compose 파일의 복사본을 만드는 명령입니다. 문제가 생겼을 때 Nginx를 추가하기 전 구성으로 돌아가기 위해서입니다.

## 2. Nginx 설정 파일 준비

```bash
mkdir -p nginx/conf.d
nano nginx/conf.d/00-observability.conf
```

아래를 저장합니다. 이 파일은 Nginx의 `http` 범위에서 읽히므로 로그 형식·캐시 공간·요청 제한 구역을 둡니다.

```nginx
log_format study
  'time=$time_iso8601 status=$status method=$request_method '
  'uri="$request_uri" cache=$upstream_cache_status '
  'rate_limit=$limit_req_status request_time=$request_time '
  'upstream_time=$upstream_response_time upstream="$upstream_addr"';

access_log /dev/stdout study;
error_log /dev/stderr notice;

proxy_cache_path /var/cache/nginx
  levels=1:2
  keys_zone=petclinic_cache:10m
  inactive=10m
  max_size=100m
  use_temp_path=off;

limit_req_zone $binary_remote_addr zone=per_ip_rate:10m rate=5r/s;
```

`limit_req_log_level notice;`로 요청 제한 사실을 남길 예정이므로, error log도 `notice` 이상을 출력하게 했습니다. `warn`으로 두면 `notice` 수준의 제한 메시지가 화면에 보이지 않을 수 있습니다. access log의 `rate_limit=REJECTED`도 함께 확인하므로, 두 로그에서 같은 차단을 교차 확인할 수 있습니다.

다음으로 실제 요청을 받는 `server` 설정을 만듭니다.

```bash
nano nginx/conf.d/default.conf
```

```nginx
server {
  listen 80;
  server_tokens off;
  client_max_body_size 1k;
  limit_req_status 429;
  limit_req_log_level notice;

  add_header X-Content-Type-Options "nosniff" always;
  add_header X-Frame-Options "SAMEORIGIN" always;
  add_header Referrer-Policy "strict-origin-when-cross-origin" always;

  # GET·HEAD만 허용하는 Nginx 자체 실습 경로
  location = /study/read-only {
    if ($request_method !~ ^(GET|HEAD)$) { return 405; }
    return 204;
  }

  # CSS·이미지·JavaScript만 캐시한다.
  location ~* \.(?:css|js|png|jpe?g|gif|svg|ico)$ {
    proxy_pass http://app:8080;
    proxy_cache petclinic_cache;
    proxy_cache_valid 200 5m;
    proxy_cache_methods GET HEAD;
    proxy_cache_bypass $arg_bypass_cache;
    proxy_no_cache $arg_bypass_cache;
    add_header X-Cache-Status $upstream_cache_status always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }

  location / {
    limit_req zone=per_ip_rate burst=10 nodelay;
    proxy_pass http://app:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

`app:8080`의 `app`은 Compose 서비스명입니다. 현재 파일에서 앱 서비스명이 다르면 그 이름으로 바꿉니다.

## 3. Compose에 Nginx·앱 내부 포트·네트워크 반영

`docker-compose.yml`을 열어 기존 `postgres`의 이미지·환경 변수·Named Volume 설정은 유지합니다. 그 위에 아래 구조가 되도록 추가·수정합니다.

```yaml
services:
  app:
    image: spring-petclinic:1.0
    environment:
      SPRING_PROFILES_ACTIVE: postgres
      POSTGRES_URL: jdbc:postgresql://postgres:5432/petclinic
      POSTGRES_USER: petclinic
      POSTGRES_PASS: petclinic
    expose:
      - "8080"
    depends_on:
      postgres:
        condition: service_healthy
    networks: [private]

  postgres:
    # 기존 image, environment, volume은 유지
    expose:
      - "5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U petclinic -d petclinic"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [private]

  nginx:
    image: nginx:stable-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - nginx-cache:/var/cache/nginx
    depends_on:
      - app
    networks: [public, private]

networks:
  public:
  private:
    internal: true

volumes:
  nginx-cache:
```

**기존 postgres의 `ports:` 줄은 직접 삭제**합니다. 기존 PostgreSQL `volumes:` 줄은 삭제하지 않습니다. 여러 Compose 파일을 쓰는 경우 override 파일에도 `ports:`가 남아 있을 수 있으므로, 최종 결과는 다음 명령으로 확인합니다.

앱에도 `ports:`가 있다면 삭제하고 `expose: "8080"`만 남깁니다. `expose`는 컨테이너끼리 쓸 포트를 나타낼 뿐 호스트 포트를 열지 않습니다. 위의 app 환경 변수 이름·이미지 태그는 3주차 실제 Compose 파일과 다를 수 있으므로, 기존 값을 유지한 채 **DB 주소의 host만 `postgres`인지** 확인합니다.

`condition: service_healthy`를 쓴다면 PostgreSQL에 위 `healthcheck`가 반드시 있어야 합니다. `petclinic` 부분은 3주차에서 실제로 사용한 DB 사용자·DB 이름으로 맞춥니다. healthcheck를 추가하지 않을 경우에는 app의 `depends_on`을 단순 목록(`- postgres`)으로 바꾸되, 그 방식은 PostgreSQL이 *시작*되기만 기다릴 뿐 연결을 받을 준비까지 보장하지는 않습니다.

## 4. 적용 전 최종 설정 검사

```bash
docker compose config
docker compose run --rm --no-deps nginx nginx -t
```

아래를 확인합니다.

- `nginx`에만 `80:80` 포트 매핑이 있다.
- `app`, `postgres`에는 호스트 포트 매핑이 없다.
- `app`은 `private`, Nginx는 `public`과 `private` 네트워크에 있다.
- PostgreSQL Named Volume이 유지된다.
- `nginx -t`에 `syntax is ok`, `test is successful`이 나온다.

`docker compose run --rm --no-deps nginx nginx -t`는 Nginx를 계속 실행하지 않고, 설정 파일을 읽어 **문법만 검사한 뒤 컨테이너를 제거**합니다. Nginx가 아직 실행 전이거나 설정 오류로 시작에 실패해도 쓸 수 있으므로, `up -d`보다 먼저 실행합니다. 문법이나 들여쓰기가 이상하면 이 단계에서 멈추고 수정합니다.

## 5. 컨테이너 실행과 연결 구조 확인

```bash
docker compose up -d
docker compose ps
curl -i http://localhost/
curl -i http://localhost:8080/ || true
```

| 확인 | 기대 결과 |
| --- | --- |
| `docker compose ps` | nginx·app·postgres가 모두 실행 중 |
| `localhost/` | PetClinic 화면 또는 `200` |
| `localhost:8080/` | 연결 실패. 앱은 실행 중이지만 호스트 포트가 없음 |

`localhost:8080`이 다른 프로그램 때문에 열릴 수도 있습니다. 따라서 접속 결과만 보지 말고 `docker compose ps`의 `PORTS` 열에서 app에 호스트 포트가 없는지 함께 확인합니다.

## 6. 정적 파일 캐시 확인

브라우저의 개발자 도구 Network 탭에서 PetClinic이 실제로 불러오는 CSS·이미지·JS 파일 하나를 고릅니다. 아래의 `<정적-파일-경로>`를 그 경로로 바꿉니다.

```bash
STUDY_ID=$(date +%s)
ASSET="http://localhost/<정적-파일-경로>?study=$STUDY_ID"

# 캐시를 우회한 요청: 매번 PetClinic까지 전달
curl -sS -o /dev/null -w 'no-cache=%{time_total}s\n' "$ASSET&bypass_cache=1"
time sh -c 'seq 1 100 | xargs -P 20 -I{} curl -sS -o /dev/null "$1"' \
  sh "$ASSET&bypass_cache=1"

# 캐시 사용: 첫 요청은 MISS, 이후 요청은 HIT
curl -sS -D - -o /dev/null "$ASSET" | grep -iE 'HTTP/|X-Cache-Status'
curl -sS -o /dev/null -w 'cache=%{time_total}s\n' "$ASSET"
time sh -c 'seq 1 100 | xargs -P 20 -I{} curl -sS -o /dev/null "$1"' \
  sh "$ASSET"

docker compose logs --since 5m --no-log-prefix nginx | \
  grep "study=$STUDY_ID" | grep -Eo 'cache=(BYPASS|MISS|HIT)' | sort | uniq -c
```

작은 로컬 파일에서는 시간 차이가 작을 수 있습니다. 이때는 `BYPASS`가 많고, 캐시 사용에서는 `MISS` 하나 뒤 `HIT`가 많이 나오는지가 핵심입니다.

## 7. 로그과 요청 제한 확인

```bash
docker compose logs --tail 80 nginx
docker compose logs --tail 80 app
docker compose logs --tail 80 postgres

seq 1 50 | xargs -P 20 -I{} sh -c \
  'curl -sS -o /dev/null -w "%{http_code}\n" http://localhost/' | sort | uniq -c

docker compose logs --since 2m nginx | \
  grep -E 'rate_limit=REJECTED|status=429'
```

정상 요청은 `200`, 제한을 넘긴 요청은 `429`가 나와야 합니다. `rate_limit=REJECTED`가 보이면 PetClinic에 보내기 전 Nginx가 거부한 것입니다.

## 8. 앞단 정책 확인

```bash
# 보안 헤더와 Nginx 버전 노출 확인
curl -sS -D - -o /dev/null http://localhost/ | \
  grep -iE '^(server|x-content-type-options|x-frame-options|referrer-policy):'

# 읽기 전용 경로의 TRACE 요청은 405
curl -i -X TRACE http://localhost/study/read-only

# 1KiB보다 큰 본문은 413
head -c 2048 /dev/zero | tr '\0' 'a' | \
  curl -i -X POST --data-binary @- http://localhost/owners/new
```

`server_tokens off`는 `Server` 헤더 자체를 없애는 것이 아니라 버전 번호를 숨깁니다. `413` 요청은 Nginx에서 먼저 막히므로 PetClinic 로그에는 해당 POST 요청이 남지 않아야 합니다.

```bash
# 405·413은 Nginx가 직접 돌려준 응답인지 access log로 확인한다.
docker compose logs --since 2m --no-log-prefix nginx | \
  grep -E 'status=(405|413)'

# 413 요청은 PetClinic까지 전달되지 않아야 한다.
docker compose logs --since 2m app
```

성공 기준은 `TRACE` 요청이 `405`, 2 KiB POST가 `413`이며, Nginx 로그에는 두 상태 코드가 남는 것입니다. `413` POST는 app 로그에 남지 않아야 합니다. 반면 `405`는 `/study/read-only`라는 **Nginx 자체 실습 경로**에서 응답하므로 PetClinic 기능을 막지 않습니다.

## 9. 502 장애와 복구

```bash
docker compose stop app
curl -i http://localhost/
docker compose logs --tail 80 nginx

docker compose start app
docker compose logs -f app
```

Spring 기동 완료 로그가 나온 뒤 `Ctrl+C`로 로그 보기를 종료하고 다시 요청합니다.

```bash
curl -i http://localhost/
```

| 시점 | 기대 결과 |
| --- | --- |
| app 중지 뒤 | Nginx는 실행 중이지만 `502 Bad Gateway` |
| Nginx error log | `connect() failed` 또는 upstream 연결 관련 오류 |
| app 재시작 뒤 | PetClinic 준비 완료 후 다시 `200` |

## 10. 설정 변경을 반영하거나 되돌리기

```bash
cp nginx/conf.d/default.conf nginx/conf.d/default.conf.before-test
docker compose exec nginx nginx -t
docker compose exec nginx nginx -s reload
```

Nginx 설정 파일만 고쳤다면 `reload`를 사용합니다. 포트·볼륨·이미지·환경 변수처럼 컨테이너 자체 설정을 바꿨다면 아래처럼 Nginx만 재생성합니다.

```bash
docker compose up -d --force-recreate nginx
```

잘못된 설정을 넣었다면 복사본을 복원한 뒤 다시 문법 검사하고 reload합니다.

```bash
cp nginx/conf.d/default.conf.before-test nginx/conf.d/default.conf
docker compose exec nginx nginx -t
docker compose exec nginx nginx -s reload
```
