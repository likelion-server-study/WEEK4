# 03. 실습 — Nginx 연결·비공개·캐시·보호·장애 복구

3주차의 PostgreSQL 이미지·환경 변수·Named Volume은 유지한다. 이 문서는 기존 파일을 통째로 덮어쓰지 않고, **추가하거나 교체할 부분만** 보여 준다.

## 이 문서를 보는 방법

실습에는 다음 화면을 사용한다. 코드 블록 위의 **작업 화면**을 먼저 확인한다.

| 표시 | 실제로 작업할 곳 | 하는 일 |
| --- | --- | --- |
| 터미널 A — 로그 관찰 | WSL2 Ubuntu에서 **PetClinic 폴더**로 이동한 첫 번째 터미널 | `docker compose logs -f`를 계속 띄워 로그 관찰 |
| 터미널 B — 명령 실행 | 같은 PetClinic 폴더를 연 두 번째 터미널 | `docker`, `curl`, `mkdir` 같은 명령 입력 |
| nano 편집 화면 | 터미널 B에서 `nano 파일경로`를 실행하면 열리는 화면 | YAML·Nginx 설정·HTML 추가 및 수정 |
| PC 브라우저 | Windows의 Chrome·Edge 등 | `http://localhost:8080` 화면 확인 |
| 휴대폰 브라우저 | 같은 Wi-Fi에 연결된 휴대폰 | 선택 외부 접속 시험 |

터미널을 두 개 쓰는 이유는 역할이 다르기 때문이다. 터미널 A는 실행 로그가 계속 출력되어 다른 명령을 입력하기 불편하므로 **관찰용**으로 두고, 터미널 B에서 요청·설정 검사 같은 **실행 명령**을 입력한다. 서로 다른 서버가 아니라 같은 컴퓨터의 같은 PetClinic 폴더를 보여 주는 창 두 개다.

이번 실습의 PetClinic은 `docker compose up -d`로 백그라운드 실행한다. 따라서 터미널 A를 닫아도 앱 컨테이너가 바로 종료되지는 않는다. 터미널 A는 로그를 편하게 보기 위한 선택 사항이며, 터미널 하나만 쓴다면 `logs -f`를 확인한 뒤 `Ctrl+C`로 로그 보기만 끝내고 다음 명령을 입력해도 된다.

두 Ubuntu 터미널을 열고 모두 **3주차에서 사용한 PetClinic 폴더**로 이동한다. 이후 별도 안내가 없는 `bash` 명령은 터미널 B에 입력한다.

```bash
# 현재 위치가 PetClinic 폴더인지 파일 목록으로 확인한다.
ls
```

정상이면 `Dockerfile`, `docker-compose.yml`, `src` 등이 보인다. 개인마다 저장 위치가 다르므로 이 문서에서는 절대경로나 사용자명을 사용하지 않고 이 위치를 모두 **PetClinic 폴더**라고 부른다. 명령 앞의 `$`나 설명용 주석은 직접 입력할 필요가 없다.

파일을 수정할 때는 터미널 B에서 안내된 `nano 파일경로`를 실행한다. nano 화면에서 내용을 수정한 뒤 다음 순서로 저장하고 나온다.

```text
Ctrl+O → Enter : 저장
Ctrl+X         : nano 종료
```

## 시작 전. 이론의 구성 요소를 실습 서비스에 대응하기

이론에서 구분한 프로그램은 Compose에서 다음 서비스로 실행한다.

| 이론의 역할 | 실습 대상 |
| --- | --- |
| 웹 서버·리버스 프록시 | `nginx` 서비스 |
| 웹 애플리케이션 | PetClinic의 Spring 코드 |
| WAS | `app` 안의 내장 Tomcat |
| 앱 서버 | PetClinic과 내장 Tomcat이 함께 실행되는 `app` 서비스 |
| DB 서버 | `postgres` 서비스 |

이론 마지막의 “Docker를 사용하지 않는 회사 환경의 연결 방식”은 현재 Compose 구조와 비교하기 위한 참고 내용이므로 별도 실습은 하지 않는다.

## 0. 실습 공통: 응답과 로그로 성공 여부 판단하기

각 단계에서는 화면이나 상태 코드만 보지 않고 요청이 어디까지 전달됐는지 로그로 확인한다. 1단계에서 로그 설정을 만든 뒤부터 다음 기준을 공통으로 사용한다.

| 확인 대상 | 확인하는 것 |
| --- | --- |
| `curl` 응답 | 사용자가 받은 HTTP 상태·헤더·응답 시간 |
| Nginx access log | 상태 코드, 캐시 상태, 요청 제한 결과, app 전달 주소 |
| Nginx error log | upstream 연결 실패 같은 오류 원인 |
| Tomcat access log | 요청이 PetClinic app까지 도착했는지 |
| PostgreSQL 로그 | DB가 연결을 받을 준비가 됐는지 |

시험 요청에는 `?study=step번호-이름`을 붙인다. 그러면 섞여 있는 로그에서도 같은 요청만 찾을 수 있다.

**작업 화면: 터미널 B · 위치: PetClinic 폴더**

```bash
# 세 서비스의 가장 최근 로그 30줄만 모아 기동·오류 상태를 빠르게 확인한다.
docker compose logs --tail 30 nginx app postgres

# 최근 2분 동안 발생한 Nginx 로그만 좁혀서 확인한다.
docker compose logs --since 2m nginx
```

**작업 화면: 터미널 A — 새 로그를 계속 관찰**

```bash
# 새로 생기는 Nginx 로그를 실시간으로 확인한다.
docker compose logs -f nginx
```

`Ctrl+C`는 로그 보기만 끝내며 컨테이너를 중지하지 않는다. 이후 단계에서는 필요한 서비스·시간·`study` 값만 골라 확인한다.

정상이라면 첫 명령은 서비스별 마지막 로그를, 두 번째는 최근 2분의 Nginx 로그를 보여 준다. 세 번째는 명령이 끝나지 않고 새 로그를 기다리는 것이 정상이며, 확인 후 `Ctrl+C`를 누른다. 아직 컨테이너를 실행하지 않았다면 로그가 없거나 서비스가 없다는 메시지가 나올 수 있으므로 1단계 이후 사용한다.

## 1. Compose에 Nginx·app을 추가해 함께 실행하기

### 1-1. 현재 구성 확인과 원본 백업

> **이 단계에서 검사하는 것:** 수정할 Compose 파일이 있는지 확인하고, 문제가 생겼을 때 돌아갈 원본 백업을 만든다.

1단계에서는 `docker-compose.yml`과 `docker-compose.override.yml`을 수정한다. 잘못 수정했을 때 원래 파일로 돌아갈 수 있도록 먼저 두 파일을 복사해 둔다.

**작업 화면: 터미널 B · 위치: PetClinic 폴더**

```bash
# 백업 파일 이름에 붙일 현재 날짜와 시각을 만든다.
BACKUP_SUFFIX=$(date +%Y%m%d-%H%M%S)
# 기본 Compose 파일을 수정 전 상태로 복사한다.
cp docker-compose.yml "docker-compose.yml.before-week4-$BACKUP_SUFFIX"
# override Compose 파일을 수정 전 상태로 복사한다.
cp docker-compose.override.yml "docker-compose.override.yml.before-week4-$BACKUP_SUFFIX"
# 두 백업 파일이 실제로 만들어졌는지 확인한다.
ls *before-week4-$BACKUP_SUFFIX
```

| 명령 부분 | 의미 |
| --- | --- |
| `date +%Y%m%d-%H%M%S` | 현재 시각을 `20260802-153000` 같은 글자로 만든다. |
| `BACKUP_SUFFIX=...` | 그 글자를 두 백업 파일이 함께 사용할 이름으로 저장한다. |
| `cp 원본 백업본` | 원본은 그대로 두고 같은 내용의 백업 파일을 만든다. |
| `ls *before-week4-...` | 실제로 생성된 백업 파일 두 개를 보여 준다. |

마지막 출력에 다음처럼 두 파일이 보이면 정상이다.

```text
docker-compose.yml.before-week4-날짜
docker-compose.override.yml.before-week4-날짜
```

### 1-2. PostgreSQL의 기존 데이터 유지와 준비 상태 확인

> **이 단계에서 검사하는 것:** 3주차 PostgreSQL 데이터 볼륨을 그대로 유지하면서, DB가 실제 연결을 받을 준비가 된 뒤 app이 시작되도록 설정한다.

현재 `mysql` 서비스는 4주차에서 사용하지 않는다. 설정은 삭제하지 않고, 기존에 실행 중인 MySQL까지 멈추기 위해 현재 Compose 컨테이너를 먼저 내린다.

**작업 화면: 터미널 B**

```bash
# 실행 중인 기존 Compose 컨테이너를 종료하되 DB 볼륨은 보존한다.
docker compose down
```

여기에는 `-v`를 붙이지 않으므로 PostgreSQL Named Volume은 유지된다. 이후 모든 실행 명령에서 `postgres app nginx`만 지정하므로 Compose 파일의 `mysql:` 설정은 남아 있어도 MySQL 컨테이너와 호스트 3306은 열리지 않는다.

기존 `postgres` 서비스에서는 `ports: ["5432:5432"]` 두 줄을 삭제하고 다음 항목을 추가한다. 기존 `image`, `environment`는 그대로 유지한다.

**작업 화면: 터미널 B — Compose 파일을 nano로 열기**

```bash
# 기본 Compose 파일을 nano 편집기로 연다.
nano docker-compose.yml
```

nano 화면에서 `services.postgres`를 찾아 아래 내용을 추가한다.

```yaml
# postgres 서비스에 추가
expose: ["5432"]
networks: [db-net]
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U petclinic -d petclinic"]
  interval: 5s
  timeout: 5s
  retries: 20
```

| 설정 이름 | 의미 |
| --- | --- |
| `expose` | PostgreSQL이 컨테이너 내부에서 5432를 사용한다고 표시한다. 호스트에 포트를 열지는 않는다. |
| `networks` | PostgreSQL을 app과 통신할 `db-net`에 연결한다. |
| `healthcheck` | PostgreSQL이 실제 연결을 받을 준비가 됐는지 반복 검사한다. |
| `test` | `pg_isready`로 `petclinic` 사용자와 DB의 준비 상태를 검사한다. |
| `interval` | 검사를 5초마다 실행한다. |
| `timeout` | 한 번의 검사가 5초 안에 끝나지 않으면 실패로 처리한다. |
| `retries` | 최대 20번 연속 실패하면 컨테이너를 `unhealthy`로 표시한다. |

저장 후 아직 컨테이너를 실행하지 않는다. YAML 들여쓰기는 기존 `image:`·`environment:`와 같은 깊이여야 한다. 실제 성공 여부는 1-8의 `docker compose config`와 `pg_isready`에서 확인한다.

### 1-3. 새 `app` 서비스 추가

> **이 단계에서 검사하는 것:** PetClinic을 Compose의 `app` 컨테이너로 실행하고, 내부 주소 `postgres:5432`로 DB에 연결하며 Tomcat 요청 로그를 남기게 한다.

3주차 Compose에는 `app` 서비스가 없으므로 `services:` 아래에 다음 `app` 블록 전체를 새로 붙인다. 이 블록 안에 Tomcat 환경 변수와 로그 볼륨까지 포함되어 있으므로 별도의 `volumes:` 키를 또 만들지 않는다. `spring-petclinic:dockerfile`은 환경세팅에서 확인하거나 만든 이미지다.

**작업 화면: 터미널 B — Compose 파일을 nano로 열기**

```bash
# app 서비스를 추가·수정하기 위해 기본 Compose 파일을 연다.
nano docker-compose.yml
```

nano 화면에서 `services:` 아래에 다음 `app:` 블록을 추가한다.

```yaml
app:
  image: spring-petclinic:dockerfile
  environment:
    SPRING_PROFILES_ACTIVE: postgres
    POSTGRES_URL: jdbc:postgresql://postgres:5432/petclinic
    POSTGRES_USER: petclinic
    POSTGRES_PASS: petclinic
    SPRING_SQL_INIT_MODE: never
    SERVER_TOMCAT_BASEDIR: /tmp/tomcat
    SERVER_TOMCAT_ACCESSLOG_ENABLED: "true"
    SERVER_TOMCAT_ACCESSLOG_DIRECTORY: access
    SERVER_TOMCAT_ACCESSLOG_PATTERN: common
    SERVER_TOMCAT_ACCESSLOG_BUFFERED: "false"
  expose: ["8080"]
  volumes:
    - ./logs/tomcat:/tmp/tomcat
  depends_on:
    postgres:
      condition: service_healthy
  networks: [proxy-net, db-net]
```

| 설정 이름 | 의미 |
| --- | --- |
| `app` | Compose 내부에서 PetClinic 컨테이너를 부를 서비스 이름이다. Nginx도 이 이름을 사용한다. |
| `image` | 앞 주차에서 만든 PetClinic 이미지를 사용한다. |
| `SPRING_PROFILES_ACTIVE` | PetClinic이 PostgreSQL용 설정을 선택하게 한다. |
| `POSTGRES_URL` | app이 접속할 DB 주소다. `postgres`는 DB 서비스명이고 `5432`는 DB 컨테이너 내부 포트다. |
| `POSTGRES_USER`, `POSTGRES_PASS` | 3주차 PostgreSQL에 설정한 계정 정보다. |
| `SPRING_SQL_INIT_MODE` | 이미 만들어진 3주차 테이블을 다시 생성하지 않게 한다. |
| `SERVER_TOMCAT_...` | PetClinic 안의 Tomcat이 받은 HTTP 요청을 파일로 기록하게 한다. |
| `expose` | app이 내부에서 8080을 사용한다고 표시한다. 호스트에는 열지 않는다. |
| `volumes` | Tomcat 로그를 PetClinic 폴더의 `logs/tomcat`에서도 볼 수 있게 연결한다. |
| `depends_on` | PostgreSQL healthcheck가 성공한 뒤 app을 시작한다. |
| `networks` | Nginx와 통신하는 `proxy-net`, DB와 통신하는 `db-net`에 app을 모두 연결한다. |

`POSTGRES_URL`에서 `localhost`를 쓰지 않는 이유도 여기서 확인할 수 있다. app 컨테이너 안의 `localhost`는 app 자기 자신을 뜻하므로, 별도 PostgreSQL 컨테이너는 Compose 서비스명인 `postgres:5432`로 찾는다.

`SPRING_SQL_INIT_MODE: never`는 **3주차에서 테이블 생성까지 끝난 DB를 이어 쓰는 경우**에 사용한다. 빈 DB라면 이 줄을 빼고 최초 테이블 생성을 먼저 해야 한다.

저장 후 `app:`이 `postgres:` 안쪽이 아니라 `services:` 바로 아래에서 `postgres:`와 같은 깊이인지 확인한다. 실행 결과는 1-8에서 app 로그의 `Started ...`로 판정한다.

### 1-4. `nginx` 서비스와 내부 네트워크 추가

> **이 단계에서 검사하는 것:** Nginx만 호스트 `8080`을 공개하고, Nginx→app→PostgreSQL 흐름이 내부 네트워크로만 이어지도록 구성한다.

`services:` 아래에 새 `nginx` 서비스를 추가한다. 이미지 태그는 팀이 정한 값으로 통일한다.

**작업 화면: 터미널 B — Compose 파일을 nano로 열기**

```bash
# nginx 서비스와 네트워크·볼륨을 추가하기 위해 기본 Compose 파일을 연다.
nano docker-compose.yml
```

nano 화면에서 `services:` 아래에 다음 `nginx:` 블록을 추가한다.

```yaml
nginx:
  image: nginx:stable-alpine
  ports: ["8080:80"]
  volumes:
    - ./nginx/conf.d:/etc/nginx/conf.d:ro
    - nginx-cache:/var/cache/nginx
  depends_on: [app]
  networks: [proxy-net]
```

| 설정 이름 | 의미 |
| --- | --- |
| `nginx` | Compose 내부에서 Nginx 컨테이너를 부를 서비스 이름이다. |
| `image` | 공식 Nginx 이미지를 사용한다. |
| `ports: ["8080:80"]` | PC의 8080으로 받은 요청을 Nginx 컨테이너의 80으로 전달한다. 이번 구성에서 호스트에 여는 유일한 포트다. |
| 첫 번째 `volumes` | PetClinic 폴더에서 작성한 Nginx 설정을 컨테이너가 읽게 한다. `ro`는 읽기 전용이다. |
| `nginx-cache` | Nginx가 저장한 캐시 파일을 보관한다. |
| `depends_on` | app 컨테이너를 먼저 시작한다. |
| `networks` | Nginx를 app과 통신할 `proxy-net`에만 연결한다. |

`docker-compose.yml` 맨 아래에 다음 최상위 항목을 추가한다. `docker-compose.override.yml`의 `petclinic-postgres-data` 선언은 수정하지 않는다. Compose가 두 파일을 합치면 PostgreSQL 볼륨과 `nginx-cache`가 함께 남는다.

같은 nano 화면에서 파일 맨 아래의 `services:` 바깥쪽에 다음 내용을 추가한다. 앞에서 nano를 닫았다면 `nano docker-compose.yml`로 다시 연다.

```yaml
networks:
  proxy-net:
  db-net:
    internal: true

volumes:
  nginx-cache:
```

| 설정 이름 | 의미 |
| --- | --- |
| `proxy-net` | Nginx와 app이 요청을 주고받는 네트워크다. |
| `db-net` | app과 PostgreSQL이 통신하는 네트워크다. |
| `internal: true` | `db-net`을 DB 통신용 내부 네트워크로 제한한다. |
| `volumes.nginx-cache` | Nginx 캐시가 사용할 Named Volume을 만든다. |

여기까지 저장만 한다. Compose 문법과 최종 포트·네트워크 결과는 설정을 모두 작성한 뒤 1-8의 `docker compose config`에서 한 번에 확인한다.

### 1-5. Tomcat 로그 폴더 만들기

> **이 단계에서 검사하는 것:** 요청이 Nginx에서 끝났는지 PetClinic의 내장 Tomcat까지 도달했는지 비교할 앱 측 로그 저장 위치를 준비한다.

Nginx 로그만으로도 upstream 전달을 판단할 수 있지만, 캐시 HIT가 앱까지 가지 않았음을 앱 쪽에서도 확인하기 위해 Tomcat access log를 켠다. Spring Boot의 `server.tomcat.accesslog.enabled` 기본값은 `false`이므로 명시해야 한다. [Spring Boot 속성 문서](https://docs.spring.io/spring-boot/appendix/application-properties/index.html)

앞에서 app에 Tomcat access log 환경 변수와 마운트를 이미 넣었다. 이제 컨테이너의 `/tmp/tomcat/access/`와 연결될 호스트 폴더만 만든다.

**작업 화면: 터미널 B**

```bash
# PetClinic 내부 Tomcat(WAS)의 HTTP 요청 로그가 저장될 폴더를 만든다.
mkdir -p logs/tomcat/access
```

| 명령 부분 | 의미 |
| --- | --- |
| `mkdir` | 새 폴더를 만든다. |
| `-p` | 상위 폴더가 없어도 함께 만들고, 이미 있어도 오류를 내지 않는다. |
| `logs/tomcat/access` | PetClinic 안의 Tomcat 요청 로그가 저장될 호스트 폴더다. |

성공하면 아무 메시지도 나오지 않는다. `ls -ld logs/tomcat/access`를 실행했을 때 폴더 정보가 보이면 정상이다.

`buffered=false`는 학습 중 요청 직후 로그 줄 수를 비교하기 위한 설정이다. 기본 버퍼링이 켜져 있으면 정상 요청도 파일에 늦게 나타나 캐시 판정이 헷갈릴 수 있다.

### 1-6. Nginx 로그 형식 파일 만들기

> **이 단계에서 검사하는 것:** 상태코드·캐시 상태·요청 제한·처리 시간·app 전달 주소가 한 줄에 보이도록 학습용 Nginx 로그 형식을 정의한다.

PetClinic 폴더의 기존 `conf.d/`는 MySQL용이므로 건드리지 않는다. `mkdir -p nginx/conf.d` 후 `nginx/conf.d/00-observability.conf`라는 **새 파일**을 만든다.

**먼저 터미널 B에서 폴더 생성**

```bash
# Nginx 설정 파일을 보관할 폴더를 만든다.
mkdir -p nginx/conf.d
# 로그·캐시·요청 제한의 공통 정의 파일을 빈 파일로 만든다.
touch nginx/conf.d/00-observability.conf
```

| 명령 | 의미 |
| --- | --- |
| `mkdir -p nginx/conf.d` | Nginx 설정 파일을 모아 둘 폴더를 만든다. |
| `touch .../00-observability.conf` | 비어 있는 설정 파일을 새로 만든다. 이미 있으면 내용은 지우지 않는다. |

성공하면 별도 출력이 없다. `ls nginx/conf.d`에서 `00-observability.conf`가 보이면 정상이다. `00-`은 여러 `.conf` 파일 중 이 공통 설정을 먼저 읽기 쉽게 붙인 이름이고, `observability`는 로그처럼 동작을 관찰하기 위한 설정이라는 뜻이다.

**그다음 터미널 B에서 새 파일을 nano로 열기**

```bash
# 공통 로그 형식을 입력하기 위해 Nginx 관찰 설정 파일을 연다.
nano nginx/conf.d/00-observability.conf
```

nano 화면에 아래 전체 내용을 입력하고 `Ctrl+O → Enter → Ctrl+X` 순서로 저장·종료한다.

```nginx
log_format study 'time=$time_iso8601 status=$status method=$request_method '
                 'uri="$request_uri" cache=$upstream_cache_status '
                 'rate_limit=$limit_req_status request_time=$request_time '
                 'upstream_time=$upstream_response_time upstream="$upstream_addr"';
error_log /dev/stderr notice;
```

| 설정 이름 | 로그에 남기는 값 |
| --- | --- |
| `log_format study` | 아래 로그 항목들을 `study`라는 형식 이름으로 묶는다. |
| `time` | 요청을 처리한 시각 |
| `status` | 사용자에게 반환한 HTTP 상태 코드 |
| `method`·`uri` | 요청 방식과 요청 주소 |
| `cache` | 캐시 결과인 `BYPASS`, `MISS`, `HIT` |
| `rate_limit` | 요청 제한이 적용됐는지 여부 |
| `request_time` | Nginx가 요청 전체를 처리한 시간 |
| `upstream_time`·`upstream` | app 응답 시간과 실제 전달 대상 |
| `error_log ... notice` | Nginx 오류를 컨테이너 로그에 `notice` 수준부터 남긴다. |

이 파일은 여러 `server`가 공통으로 쓸 로그 형식을 정의한다. 실제로 이 형식을 사용하라는 설정은 다음 `default.conf`의 `access_log /dev/stdout study;`에 넣는다. 캐시와 요청 제한의 공통 설정도 이후 단계에서 이 파일 아래에 추가한다.

파일을 저장한다. 이 단계에서는 화면에 결과가 나타나지 않으며, 문법은 1-8의 `nginx -t`에서 확인한다.

### 1-7. Nginx 웹 서버 설정 파일 만들기

> **이 단계에서 검사하는 것:** Nginx가 컨테이너 내부 80번 포트에서 요청을 받고 `app:8080`으로 전달하며, 앞에서 정의한 학습용 로그를 실제로 기록하도록 설정한다.

1-6에서 만든 파일은 **로그 한 줄의 모양**만 정의했다. 이번 1-7에서는 Nginx가 80번 포트에서 요청을 받고 PetClinic `app:8080`으로 전달하게 만드는 **실제 웹 서버 설정**을 작성한다.

사용할 파일은 `nginx/conf.d/default.conf`다. 먼저 파일이 이미 있는지 검사한다. 있으면 백업한 뒤 수정하고, 없으면 새로 만든다.

기존 파일이 있다면 수정 전에 한 번 보관한다.

**작업 화면: 터미널 B**

```bash
# 백업 파일 이름에 붙일 현재 날짜와 시각을 만든다.
BACKUP_SUFFIX=$(date +%Y%m%d-%H%M%S)
# 기존 default.conf의 존재 여부에 따라 백업하거나 새 파일을 만든다.
if [ -f nginx/conf.d/default.conf ]; then
  # 기존 파일을 찾았다는 안내를 출력한다.
  echo "[있음] 기존 default.conf를 백업합니다."
  # 기존 웹 서버 설정을 수정 전 상태로 복사한다.
  cp nginx/conf.d/default.conf "nginx/conf.d/default.conf.before-week4-$BACKUP_SUFFIX"
else
  # 기존 파일이 없어 새로 만든다는 안내를 출력한다.
  echo "[없음] 새 default.conf를 만듭니다."
  # PetClinic 요청 처리 규칙을 적을 빈 설정 파일을 만든다.
  touch nginx/conf.d/default.conf
fi
# default.conf가 실제로 준비됐는지 파일 정보로 확인한다.
ls -l nginx/conf.d/default.conf
```

- `BACKUP_SUFFIX=...`: 이번 백업 파일명에 사용할 현재 시각을 만든다.
- `if [ -f ... ]`: 기존 `default.conf` 파일이 있는지 검사한다.
- `then` 부분: 파일이 있으면 현재 시각이 붙은 이름으로 백업한다.
- `else` 부분: 파일이 없으면 `touch`로 새 파일을 만든다.
- `cp ...`: 기존 설정을 `default.conf.before-week4-날짜`라는 이름으로 보관한다.
- `touch .../default.conf`: 파일이 없으면 새로 만들고, 이미 있으면 기존 내용은 유지한다.
- `ls -l`: 최종적으로 편집할 파일이 생겼는지 보여 준다.

마지막 출력에 `nginx/conf.d/default.conf`가 보이면 편집 준비가 끝난 것이다.

**작업 화면: 터미널 B — 새 파일을 nano로 열기**

```bash
# Nginx의 포트·프록시·요청 경로 규칙을 입력하기 위해 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면에 아래 전체 내용을 입력하고 저장·종료한다.

```nginx
server {
  listen 80;
  access_log /dev/stdout study;

  location / {
    proxy_pass http://app:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

| 설정 이름 | 의미 |
| --- | --- |
| `server` | Nginx가 요청을 받을 한 개의 웹 서버 설정 범위다. |
| `listen 80` | Nginx 컨테이너 내부 80번 포트에서 요청을 받는다. |
| `access_log /dev/stdout study` | 앞에서 만든 `study` 형식으로 요청 로그를 컨테이너 표준 출력에 남긴다. |
| `location /` | `/`로 시작하는 일반 PetClinic 요청을 처리한다. |
| `proxy_pass` | 요청을 Compose 내부의 PetClinic `app:8080`으로 전달한다. |
| `proxy_set_header` | 원래 요청의 호스트·사용자 IP·프로토콜 정보를 app에 함께 전달한다. |

파일을 저장한다. 아직 브라우저에서 열 필요는 없으며, 다음 단계에서 Nginx를 실행한 뒤 확인한다.

### 1-8. 설정 검사와 세 서비스 실행

> **이 단계에서 검사하는 것:** 필요한 파일·서비스와 설정 문법을 확인한 뒤 PostgreSQL→app→Nginx 순서로 정상 기동하고 첫 요청·로그를 검증한다.

1-8은 새 설정을 작성하는 단계가 아니다. 1-1~1-7에서 준비한 파일이 모두 있는지 확인하고, Compose·Nginx 문법을 검사한 다음 `postgres → app → nginx` 순서로 실제 실행하는 단계다.

먼저 필요한 파일 네 개가 **존재하면서 비어 있지 않은지** 확인한다.

**작업 화면: 터미널 B — 필수 파일 존재 여부 검사**

```bash
# 기본 Compose 파일이 존재하고 비어 있지 않은지 확인한다.
test -s docker-compose.yml \
  && echo "[있음] docker-compose.yml" \
  || echo "[없음] docker-compose.yml"

# override Compose 파일이 존재하고 비어 있지 않은지 확인한다.
test -s docker-compose.override.yml \
  && echo "[있음] docker-compose.override.yml" \
  || echo "[없음] docker-compose.override.yml"

# Nginx 관찰 설정 파일이 존재하고 비어 있지 않은지 확인한다.
test -s nginx/conf.d/00-observability.conf \
  && echo "[있음] 00-observability.conf" \
  || echo "[없음] 00-observability.conf"

# Nginx 웹 서버 설정 파일이 존재하고 비어 있지 않은지 확인한다.
test -s nginx/conf.d/default.conf \
  && echo "[있음] default.conf" \
  || echo "[없음] default.conf"
```

| 명령 부분 | 의미 |
| --- | --- |
| `test -s 파일` | 파일이 존재하고 내용도 한 글자 이상 있는지 검사한다. |
| `&& echo "[있음]"` | 검사가 성공했을 때 출력한다. |
| `|| echo "[없음]"` | 파일이 없거나 비어 있을 때 출력한다. |

네 줄이 모두 `[있음]`이어야 다음으로 진행한다. `[없음]`이 하나라도 나오면 실행하지 말고 해당 파일을 만든 앞 단계로 돌아간다.

그다음 Compose 문법과 서비스 정의를 확인한 뒤 PostgreSQL·app을 먼저 실행한다. Compose 검사가 실패하면 컨테이너를 실행하지 말고 표시된 YAML 줄을 먼저 고친다. app의 `Started ...` 로그를 확인한 다음 임시 Nginx 컨테이너로 문법을 검사하고 Nginx 서비스를 실행한다.

**작업 화면: 터미널 B — 실행 명령**

```bash
# 합쳐진 Compose 설정의 문법 오류가 없는지 확인한다.
docker compose config -q && echo "Compose 설정 정상"
# 최종 Compose 설정에 등록된 서비스 이름을 변수에 저장한다.
SERVICES=$(docker compose config --services)
# postgres 서비스가 정확한 이름으로 등록됐는지 확인한다.
printf '%s\n' "$SERVICES" | grep -qx postgres \
  && echo "[있음] postgres 서비스" || echo "[없음] postgres 서비스"
# app 서비스가 정확한 이름으로 등록됐는지 확인한다.
printf '%s\n' "$SERVICES" | grep -qx app \
  && echo "[있음] app 서비스" || echo "[없음] app 서비스"
# nginx 서비스가 정확한 이름으로 등록됐는지 확인한다.
printf '%s\n' "$SERVICES" | grep -qx nginx \
  && echo "[있음] nginx 서비스" || echo "[없음] nginx 서비스"
```

| 명령 부분 | 의미 |
| --- | --- |
| `config -q` | 합쳐진 Compose 설정의 문법만 검사하고, 정상이면 긴 설정 내용은 출력하지 않는다. |
| `SERVICES=$(... --services)` | Compose에 정의된 서비스 이름을 `SERVICES`에 저장한다. |
| `grep -qx 서비스명` | 서비스 목록에 해당 이름이 한 줄로 정확히 있는지 검사한다. |
| `&& ... || ...` | 서비스가 있으면 `[있음]`, 없으면 `[없음]`을 출력한다. |

`Compose 설정 정상`과 서비스 세 개의 `[있음]`이 모두 출력돼야 한다. `[없음]`이 나오면 `docker-compose.yml`의 `services:` 들여쓰기와 이름을 고친 뒤 다시 검사한다.

모두 정상일 때만 PostgreSQL과 PetClinic을 실행한다.

```bash
# DB와 PetClinic 앱을 먼저 백그라운드에서 실행한다.
docker compose up -d postgres app
```

`up -d postgres app`은 두 서비스를 백그라운드로 실행한다. 아직 Nginx는 실행하지 않는다.

**작업 화면: 터미널 A — app 기동 로그 관찰**

```bash
# app이 완전히 기동되어 Started 문구가 나오는지 실시간으로 확인한다.
docker compose logs -f --since 1m app
```

`Started ...`가 보이면 app 기동이 완료된 것이다. 터미널 A는 그대로 두거나 `Ctrl+C`로 로그 보기만 끝낸다.

**작업 화면: 터미널 B — app 기동을 확인한 뒤 계속 실행**

**① Nginx 설정을 검사하고 실행한다.**

```bash
# 실제 Nginx를 띄우기 전에 임시 컨테이너에서 설정 문법을 검사한다.
docker compose run --rm --no-deps nginx nginx -t
# 문법 검사가 성공한 Nginx를 백그라운드에서 실행한다.
docker compose up -d nginx
# 세 서비스의 실행 상태와 호스트 공개 포트를 확인한다.
docker compose ps
```

`nginx -t`가 성공한 뒤에만 Nginx를 실행한다. `docker compose ps`에서는 `nginx`에만 `0.0.0.0:8080->80/tcp`가 있고, `app`과 `postgres`에는 호스트 포트 표시가 없는지 본다.

**② Nginx 경유 응답과 DB 준비 상태를 확인한다.**

```bash
# Nginx의 호스트 포트로 요청해 PetClinic이 200으로 열리는지 확인한다.
curl -i http://localhost:8080/
# petclinic 사용자·DB 기준으로 PostgreSQL이 연결을 받을 준비가 됐는지 확인한다.
docker compose exec postgres pg_isready -U petclinic -d petclinic
```

첫 명령은 Nginx를 거쳐 PetClinic 화면이 `HTTP/1.1 200`으로 열리는지 확인한다. 두 번째 명령은 PostgreSQL이 `accepting connections` 상태인지 확인한다.

**③ 학습용 요청 한 건을 보내고, 그 요청의 Nginx 로그만 찾는다.**

```bash
# 로그에서 쉽게 찾을 수 있는 표식을 붙여 Nginx에 요청 한 건을 보낸다.
curl -sS -o /dev/null 'http://localhost:8080/?study=step1-log-once'
# 최근 Nginx 로그 중 방금 보낸 표식이 있는 요청만 골라 로그 형식을 확인한다.
docker compose logs --since 30s --no-log-prefix nginx | \
  grep 'study=step1-log-once'
```

이 요청은 로그 형식이 제대로 적용됐는지 확인하기 위한 표식이다. 모든 서비스의 최근 로그를 다시 한꺼번에 볼 필요 없이, 방금 보낸 요청 한 건만 찾는다. 서비스별 로그를 넓게 보는 방법은 5단계에서 다룬다.

| 명령 | 확인하는 것 |
| --- | --- |
| `docker compose run ... nginx -t` | 임시 Nginx 컨테이너로 설정 문법을 검사한다. 검사 후 임시 컨테이너는 삭제된다. |
| `docker compose up -d nginx` | 실제 Nginx 컨테이너를 백그라운드로 실행한다. |
| `docker compose ps` | 세 서비스의 실행 상태와 호스트에 공개된 포트를 확인한다. |
| `curl -i` | Nginx 8080을 통해 PetClinic 응답과 상태 코드를 확인한다. |
| `pg_isready -U petclinic -d petclinic` | `petclinic` 사용자·DB 기준으로 PostgreSQL이 연결을 받을 준비가 됐는지 확인한다. |
| 마지막 두 명령 | 시험 요청을 한 번 보내고 Nginx 로그에서 그 요청만 찾는다. |

서비스 검사에서는 `postgres`, `app`, `nginx`가 모두 `[있음]`이어야 한다. 기존 `mysql` 정의가 파일에 남아 있어도 실행 명령에서 지정하지 않았으므로 `docker compose ps`에는 이번에 실행한 세 서비스만 보여야 한다. 마지막 `study=step1-log-once` 요청은 학습용 `study` 형식으로 한 줄만 보여야 한다. 두 줄 이상 보이면 04-트러블슈팅의 중복 access log 항목을 따른다.

Nginx 시작 로그에 `can not modify /etc/nginx/conf.d/default.conf (read-only file system?)`이 보일 수 있다. 설정 폴더를 `:ro`로 연결했기 때문에 이미지의 시작 스크립트가 파일을 수정하지 못했다는 안내다. 바로 뒤의 `nginx -t`가 성공하고 Nginx 컨테이너가 실행 중이라면 실습 실패가 아니다.

정상 결과는 다음과 같다.

- `nginx -t`: `syntax is ok`, `test is successful`
- `docker compose ps`: `postgres`, `app`, `nginx`가 `Up`이며 PostgreSQL은 `healthy`
- `curl -i`: 첫 줄이 `HTTP/1.1 200`
- `pg_isready`: `accepting connections`

`-U petclinic -d petclinic`을 생략하면 명령을 실행한 계정 이름(예: `root`)으로 PostgreSQL에 접속하려고 시도할 수 있다. 그때 PostgreSQL 로그에 `role "root" does not exist`가 남아도, 바로 앞의 `accepting connections`와 Compose healthcheck가 정상이라면 DB 자체의 장애는 아니다. 이 실습에서는 위처럼 사용자와 DB 이름을 명시한다.

이 시점의 `Server: nginx/버전` 헤더는 정상이다. 버전 번호를 숨기는 `server_tokens off`는 4단계에서 적용한다.
- 마지막 로그 검색: `status=200`, `study=step1-log-once`, `upstream="...:8080"` 포함

## 2. app·PostgreSQL은 감추고 Nginx만 공개하기

### 2-1. 공개 주소와 내부 주소 확인

> **이 단계에서 검사하는 것:** 사용자는 `localhost:8080`의 Nginx로 접속하고, app과 PostgreSQL은 Compose 내부 주소로만 통신하는지 확인한다.

1단계에서 작성한 포트와 네트워크 구성을 실제 컨테이너에 반영한다. 호스트의 `localhost:8080`은 Nginx에 연결되고, `app:8080`과 `postgres:5432`는 컨테이너 사이에서만 사용한다.

**작업 화면: 터미널 B — 컨테이너 재생성**

```bash
# 현재 Compose 설정에 문법 오류가 없는지 먼저 확인한다.
docker compose config -q && echo "Compose 설정 정상"
# 포트·네트워크 변경 사항을 적용하도록 세 컨테이너를 다시 만든다.
docker compose up -d --force-recreate app postgres nginx
```

| 명령 부분 | 의미 |
| --- | --- |
| `config -q` | Compose 문법을 조용히 검사한다. 정상일 때만 뒤의 문구가 출력된다. |
| `up -d` | 지정한 서비스를 백그라운드로 실행한다. |
| `--force-recreate` | 기존 컨테이너가 있어도 지금 저장한 포트·네트워크 설정으로 다시 만든다. |

**작업 화면: 터미널 A — app 기동 로그 관찰**

```bash
# 재생성된 app이 Started 상태까지 정상 기동하는지 실시간으로 확인한다.
docker compose logs -f --since 1m app
```

| 명령 부분 | 의미 |
| --- | --- |
| `logs -f app` | app의 새 로그를 계속 보여 준다. |
| `--since 1m` | 최근 1분 이후 로그부터 보여 준다. |

`Started ...`가 보이면 `Ctrl+C`로 로그 보기만 종료한다.

**작업 화면: 터미널 B — 상태와 응답 확인**

```bash
# 세 서비스가 모두 실행 중이고 Nginx만 호스트 포트를 공개했는지 확인한다.
docker compose ps
# Nginx를 통해 요청해 PetClinic 응답이 정상인지 확인한다.
curl -i 'http://localhost:8080/?study=step2'
```

| 명령 | 확인하는 것 |
| --- | --- |
| `docker compose ps` | app·postgres·nginx가 모두 실행 중인지 확인한다. |
| `curl -i` | Nginx의 호스트 8080으로 요청하고 응답 헤더·본문을 함께 본다. |

세 서비스가 실행 중이고 `localhost:8080`에서 PetClinic 응답이 나오면 호스트의 Nginx 입구가 열린 것이다.

추가로 **PC 브라우저** 주소창에 `http://localhost:8080`을 입력한다. PetClinic 첫 화면이 열리면 정상이다. 이 주소의 8080은 app이 아니라 Nginx에 게시한 호스트 포트다.

### 2-2. Nginx가 app으로 전달했는지 로그로 확인

> **이 단계에서 검사하는 것:** 같은 요청이 Nginx access log와 Tomcat access log에 모두 남는지 비교해 Nginx가 app까지 전달했음을 증명한다.

1단계에서 `default.conf`에 넣은 `proxy_pass http://app:8080`이 실제로 작동했는지 같은 `study=step2` 요청을 두 로그에서 찾는다.

**작업 화면: 터미널 B**

```bash
# 최근 Nginx 로그에서 2단계 시험 요청만 찾아 app 전달 주소를 확인한다.
docker compose logs --since 2m --no-log-prefix nginx | \
  grep 'study=step2'

# Tomcat access log에서 같은 요청을 찾아 PetClinic까지 도달했는지 확인한다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -h 'study=step2' {} +
```

| 명령 부분 | 의미 |
| --- | --- |
| `logs --since 2m nginx` | 최근 2분의 Nginx 로그만 가져온다. |
| `--no-log-prefix` | Compose가 앞에 붙이는 서비스 이름을 빼 로그 본문을 쉽게 검색한다. |
| `grep 'study=step2'` | 이번 시험 요청이 들어간 줄만 고른다. |
| `find ... access_log*.log` | Tomcat access log 파일을 찾는다. |
| `-exec grep ...` | 찾은 파일 안에서 같은 시험 요청을 검색한다. |

Nginx 로그의 같은 요청에 `status=200`과 `upstream="app의-내부주소:8080"`이 있고 Tomcat access log에도 `study=step2`가 있으면, 요청이 Nginx에서 app까지 전달된 것이다. `--since 2m`은 오래된 로그를 제외하고 최근 2분만 검색한다.

### 2-3. app·PostgreSQL 비공개 판정

> **이 단계에서 검사하는 것:** app과 PostgreSQL은 실행 중이지만 호스트 포트가 게시되지 않아 외부에서 직접 접근할 수 없는 상태인지 확인한다.

두 서비스가 꺼져 있어서 접속할 수 없는 것이 아니라, 실행 중이지만 호스트 게시 포트가 없다는 것을 확인한다.

**작업 화면: 터미널 B**

```bash
# 전체 서비스의 실행 상태와 실제 호스트 포트 게시 결과를 다시 확인한다.
docker compose ps
# app의 내부 8080 포트가 호스트에 게시됐는지 조회한다. 출력이 없어야 정상이다.
docker compose port app 8080
# postgres의 내부 5432 포트가 호스트에 게시됐는지 조회한다. 출력이 없어야 정상이다.
docker compose port postgres 5432
```

| 명령 | 확인하는 것 |
| --- | --- |
| `docker compose ps` | app과 postgres가 꺼진 것이 아니라 실행 중인지 확인한다. |
| `port app 8080` | app 내부 8080과 연결된 호스트 포트가 있는지 확인한다. |
| `port postgres 5432` | PostgreSQL 내부 5432와 연결된 호스트 포트가 있는지 확인한다. |

`docker compose ps`에서는 app·postgres가 실행 중이어야 한다. 반면 뒤의 두 명령에는 실제 `IP:호스트포트`가 나오지 않아야 한다. Compose 버전에 따라 아무것도 출력하지 않거나 `:0`처럼 보일 수 있다. 호스트에 게시된 포트는 Nginx의 `8080` 하나여야 한다.

예상 형태는 다음과 같다. 컨테이너 이름과 IP는 환경마다 달라질 수 있다.

```text
nginx      0.0.0.0:8080->80/tcp
app        8080/tcp
postgres   5432/tcp
```

### 2-4. 선택: 같은 Wi-Fi의 휴대폰에서 Nginx 접속

> **이 단계에서 검사하는 것:** 같은 네트워크의 다른 기기에서도 Nginx의 공개 포트로 접속할 수 있고, 요청이 Nginx 로그에 남는지 선택적으로 확인한다.

환경세팅에서 확인한 노트북의 LAN IP를 사용해 휴대폰 브라우저에서 다음 주소를 연다.

**작업 화면: 휴대폰 브라우저 주소창**

```text
http://<노트북-LAN-IP>:8080/?study=step2-external
```

PetClinic 화면이 열리면 다른 기기에서도 Nginx 입구에 접근한 것이다. 이 시험은 app 비공개를 증명하는 절차가 아니다. app·PostgreSQL 비공개 여부는 앞의 `docker compose port` 결과로 판정한다.

**로그 확인 화면: 터미널 B**

```bash
# 최근 Nginx 로그에서 외부 장치가 보낸 시험 요청만 찾아 실제 도달 여부를 확인한다.
docker compose logs --since 5m --no-log-prefix nginx | \
  grep 'study=step2-external'
```

| 명령 부분 | 의미 |
| --- | --- |
| `logs --since 5m nginx` | 휴대폰 시험을 한 최근 5분의 Nginx 로그만 본다. |
| `grep 'study=step2-external'` | 휴대폰 주소에 붙인 시험 요청만 고른다. |

로그에 `status=200`과 app upstream이 있으면 `휴대폰 → Nginx → app` 전달도 확인한 것이다.

## 3. 정적 파일 캐시 효과 비교하기

### 3-1. 실제 캐시 대상 이미지 확인

> **이 단계에서 검사하는 것:** 동적 화면이 아니라 실제 PNG 정적 파일을 선택하고, 요청 결과가 `200`과 이미지 형식인지 확인한다.

동적 화면 대신 내용이 자주 바뀌지 않는 실제 이미지를 사용한다. 먼저 소스 파일과 실행 중 URL을 확인한다.

**작업 화면: 터미널 B**

```bash
# PetClinic 소스에서 캐시 시험에 사용할 실제 pets.png 파일 위치를 찾는다.
find src/main/resources -type f -name 'pets.png'
# 실행 중인 PetClinic의 이미지 URL이 200과 image/png로 응답하는지 확인한다.
curl -sS -D - -o /dev/null \
  http://localhost:8080/resources/images/pets.png
```

| 명령 부분 | 의미 |
| --- | --- |
| `find src/main/resources` | PetClinic의 정적 파일 폴더 아래를 검색한다. |
| `-type f -name 'pets.png'` | 폴더가 아닌 파일 중 이름이 `pets.png`인 것만 찾는다. |
| `curl -D -` | 응답 헤더를 터미널에 출력한다. |
| `-o /dev/null` | 이미지 본문은 버리고 헤더만 확인한다. |

`src/main/resources/static/resources/images/pets.png`가 검색되고 HTTP `200`과 이미지 `Content-Type`이 나오면 `/resources/images/pets.png`를 사용한다. 파일이 없다면 브라우저 개발자 도구의 Network 탭에서 실제 `.png`·`.jpg`·`.svg` 주소를 골라 아래 `IMAGE_PATH`만 바꾼다.

PC 브라우저 주소창에서도 `http://localhost:8080/resources/images/pets.png`를 열어 실제 PetClinic 이미지를 눈으로 확인한다. 터미널 응답 헤더에는 `HTTP/1.1 200`과 `Content-Type: image/png`가 보이면 정상이다.

### 3-2. 캐시 설정과 BYPASS·MISS·HIT 확인

> **이 단계에서 검사하는 것:** 캐시 우회 요청은 `BYPASS`, 새 URL의 첫 요청은 `MISS`, 같은 URL의 재요청은 `HIT`가 되는지 확인한다.

`nginx/conf.d/00-observability.conf`의 마지막에 캐시 저장 영역을 추가한다.

**작업 화면: 터미널 B — 공통 설정 파일 열기**

```bash
# 캐시 저장 공간 정의를 추가하기 위해 Nginx 관찰 설정 파일을 연다.
nano nginx/conf.d/00-observability.conf
```

nano 화면의 맨 아래에 다음 설정을 추가하고 저장·종료한다.

```nginx
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=petclinic_cache:10m
                 inactive=10m max_size=100m use_temp_path=off;
```

| 설정 이름 | 의미 |
| --- | --- |
| `proxy_cache_path` | Nginx 캐시 파일을 저장할 위치를 정한다. |
| `keys_zone` | 캐시 목록을 기억할 메모리 영역의 이름과 크기를 정한다. |
| `inactive` | 10분 동안 사용하지 않은 캐시를 정리한다. |
| `max_size` | 디스크 캐시의 최대 크기를 100MB로 제한한다. |

`nginx/conf.d/default.conf`의 일반 `location /` 앞에 정적 파일 전용 location을 추가한다. 동적 화면에는 캐시를 넣지 않는다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# 정적 파일 요청에 캐시를 적용하기 위해 Nginx 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면에서 `server {}` 안의 기존 `location /` 바로 위에 다음 블록을 추가하고 저장·종료한다.

```nginx
location ~* \.(?:css|js|png|jpe?g|gif|svg|ico)$ {
  proxy_pass http://app:8080;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_cache petclinic_cache;
  proxy_cache_valid 200 5m;
  proxy_cache_methods GET HEAD;
  proxy_cache_bypass $arg_bypass_cache;
  proxy_no_cache $arg_bypass_cache;
  add_header X-Cache-Status $upstream_cache_status always;
}
```

| 설정 이름 | 의미 |
| --- | --- |
| `location ~* ...` | CSS·JavaScript·이미지 확장자 요청만 선택한다. |
| `proxy_cache` | 앞에서 만든 `petclinic_cache`를 사용한다. |
| `proxy_cache_valid` | 상태 코드 200 응답을 5분 동안 캐시한다. |
| `proxy_cache_methods` | GET·HEAD 요청만 캐시 대상으로 삼는다. |
| `proxy_cache_bypass` | URL에 `bypass_cache` 값이 있으면 저장된 캐시를 사용하지 않는다. |
| `proxy_no_cache` | 우회 요청으로 받은 응답은 새 캐시로 저장하지 않는다. |
| `X-Cache-Status` | 응답 헤더에서 `BYPASS`, `MISS`, `HIT`를 확인하게 한다. |

설정을 검사하고 반영한다.

**작업 화면: 터미널 B**

```bash
# 수정한 캐시 설정의 Nginx 문법이 올바른지 검사한다.
docker compose exec nginx nginx -t
# 문법 검사가 성공한 설정을 실행 중인 Nginx에 반영한다.
docker compose exec nginx nginx -s reload
```

| 명령 | 의미 |
| --- | --- |
| `nginx -t` | 저장한 Nginx 설정의 문법을 검사한다. |
| `nginx -s reload` | 실행 중인 Nginx가 새 설정을 다시 읽게 한다. |

**같은 터미널 B에서 캐시 요청 실행**

```bash
# 이전 캐시와 겹치지 않도록 이번 시험만의 고유 ID를 만든다.
STUDY_ID="$(date +%s)-$$"
# 캐시 시험에 사용할 실제 이미지 경로를 변수에 저장한다.
IMAGE_PATH="resources/images/pets.png"
# 같은 URL을 반복 사용할 수 있도록 시험용 전체 주소를 만든다.
ASSET="http://localhost:8080/$IMAGE_PATH?study=$STUDY_ID"

# 캐시를 우회해 실제 이미지 형식·크기·단일 응답 시간을 확인한다.
curl -sS -D - -o /tmp/petclinic-cache-image \
  -w 'type=%{content_type} bytes=%{size_download} time=%{time_total}s\n' "$ASSET&bypass_cache=1"

# 첫 일반 요청에서 실제 X-Cache-Status가 MISS인지 확인한다.
curl -sS -D - -o /dev/null -w '일반 요청 1 time=%{time_total}s\n' "$ASSET" | \
  grep -iE 'HTTP/|X-Cache-Status|time='
# 같은 URL을 다시 요청해 실제 X-Cache-Status가 HIT인지 확인한다.
curl -sS -D - -o /dev/null -w '일반 요청 2 time=%{time_total}s\n' "$ASSET" | \
  grep -iE 'HTTP/|X-Cache-Status|time='
```

| 명령 부분 | 의미 |
| --- | --- |
| `STUDY_ID="$(date +%s)-$$"` | 현재 시각과 현재 셸 번호를 합쳐, 예전 시험 캐시와 겹치지 않을 시험 ID를 만든다. |
| `IMAGE_PATH`·`ASSET` | 반복해서 사용할 이미지 경로와 전체 URL을 저장한다. |
| `-w` | 다운로드 크기와 응답 시간을 지정한 형식으로 출력한다. |
| `bypass_cache=1` | Nginx 캐시를 일부러 우회한다. |
| `grep -iE` | HTTP 상태와 캐시 상태, 시간 줄만 골라 보여 준다. |

첫 명령의 `bypass_cache=1` 요청은 `BYPASS`다. 이 명령은 이미지 형식·크기·시간도 함께 확인하므로, 같은 BYPASS 요청을 한 번 더 보낼 필요가 없다. 그다음 일반 요청 1은 `MISS`, 같은 URL의 일반 요청 2는 `HIT`가 기대값이다. `일반 요청 1`, `일반 요청 2`는 보기 쉽게 붙인 글자일 뿐이고, 실제 판정은 `X-Cache-Status` 헤더로 한다.

예상 응답의 핵심은 다음 세 줄이다. 시간 값은 컴퓨터마다 다르다.

```text
X-Cache-Status: BYPASS
X-Cache-Status: MISS
X-Cache-Status: HIT
```

`MISS`만 반복되면 정상으로 넘기지 말고 04-트러블슈팅의 캐시 항목을 확인한다.

### 3-3. 단일 시간·반복 시간·app 전달 횟수 비교

> **이 단계에서 검사하는 것:** 캐시 사용 전후의 응답 시간뿐 아니라 Tomcat 도달 횟수까지 비교해 Nginx가 app의 요청 처리를 실제로 줄였는지 확인한다.

로컬에서는 단일 요청의 시간 차이가 작을 수 있다. 같은 실제 이미지를 300번 **순차 요청**해 누적 시간을 비교하고, 로그로 app 전달 횟수도 확인한다. 앞에서 만든 HIT 상태와 같은 `ASSET` 값을 그대로 사용한다.

**작업 화면: 같은 터미널 B — 앞 단계에서 만든 `ASSET` 변수를 그대로 사용**

```bash
# 캐시를 300번 우회했을 때 순차 요청 전체 시간을 측정한다.
time sh -c 'awk "BEGIN {for(i=1;i<=300;i++) print i}" | xargs -P 1 -I{} curl -sS -o /dev/null "$1"' \
  sh "$ASSET&bypass_cache=1"

# 같은 이미지를 캐시로 300번 처리했을 때 순차 요청 전체 시간을 측정한다.
time sh -c 'awk "BEGIN {for(i=1;i<=300;i++) print i}" | xargs -P 1 -I{} curl -sS -o /dev/null "$1"' \
  sh "$ASSET"
```

| 명령 부분 | 의미 |
| --- | --- |
| `time` | 명령 묶음의 전체 소요시간을 측정한다. |
| `awk ... 300` | 요청을 300번 실행하기 위한 숫자를 만든다. |
| `xargs -P 1` | 요청을 한 번에 하나씩 순차 실행한다. |
| 첫 번째 URL | 300번 모두 캐시를 우회한다. |
| 두 번째 URL | 앞에서 저장된 캐시를 사용한다. |

첫 번째 시간은 300번 모두 PetClinic까지 전달된 경우이고, 두 번째는 대부분 Nginx HIT인 경우다. 부하가 동시에 들어올 때의 처리량도 보고 싶다면 별도로 병렬 200회를 실행한다.

**선택 실행 화면: 같은 터미널 B**

```bash
# 캐시를 우회하는 요청 200개를 최대 20개씩 동시에 보내 전체 시간을 측정한다.
time sh -c 'awk "BEGIN {for(i=1;i<=200;i++) print i}" | xargs -P 20 -I{} curl -sS -o /dev/null "$1"' \
  sh "$ASSET&bypass_cache=1"

# 캐시를 사용하는 요청 200개를 최대 20개씩 동시에 보내 전체 시간을 측정한다.
time sh -c 'awk "BEGIN {for(i=1;i<=200;i++) print i}" | xargs -P 20 -I{} curl -sS -o /dev/null "$1"' \
  sh "$ASSET"
```

`xargs -P 20`은 최대 20개 요청을 동시에 실행한다. 순차 시험과 달리 여러 요청이 함께 들어올 때의 전체 시간을 비교한다.

순차 요청은 누적 시간 차이를 보기 쉽고, 병렬 요청은 일정 시간 동안 얼마나 처리하는지 비교하기 좋다. 시간만으로 결론 내리지 않고 다음 두 로그를 같이 센다.

**작업 화면: 터미널 B**

```bash
# 이번 시험 ID가 붙은 Nginx 로그만 찾아 BYPASS·MISS·HIT 처리 결과를 확인한다.
# 캐시 비교·반복 요청을 모두 끝낸 뒤에도 찾을 수 있도록 최근 1시간을 조회한다.
docker compose logs --since 1h --no-log-prefix nginx | \
  grep "study=$STUDY_ID" | grep -E 'cache=(BYPASS|MISS|HIT)'

# 생성된 Tomcat access log 파일과 최근 요청 내용을 확인한다.
find logs/tomcat/access -type f -name 'access_log*.log' -print -exec tail -n 20 {} \;

# 이번 시험 요청 중 PetClinic까지 전달된 전체 횟수를 센다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -h "study=$STUDY_ID" {} + | wc -l

# bypass_cache=1이 붙어 PetClinic까지 전달된 요청 횟수를 센다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -h "study=$STUDY_ID.*bypass_cache=1" {} + | wc -l

# 일반 URL 중 PetClinic까지 전달된 요청 횟수를 세어 HIT가 앱에 가지 않았는지 확인한다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -h "study=$STUDY_ID" {} + | grep -v 'bypass_cache=1' | wc -l
```

| 명령 부분 | 의미 |
| --- | --- |
| Nginx `logs` + `grep` | 이번 시험의 `BYPASS`, `MISS`, `HIT` 로그만 찾는다. |
| `tail -n 20` | Tomcat 로그의 마지막 20줄을 먼저 눈으로 확인한다. |
| `wc -l` | 검색된 요청 줄 수를 숫자로 센다. |
| `grep -v 'bypass_cache=1'` | 우회 요청을 제외하고 캐시 사용 URL만 센다. |

`BYPASS`·`MISS`에는 보통 `upstream=...`가 있고 Tomcat access log에도 같은 `study` 요청이 남는다. `HIT`에는 upstream이 `-`이거나 비어 있고, 같은 반복 수만큼의 새 Tomcat access log가 늘지 않아야 한다. 마지막 두 숫자를 비교하면 우회 요청은 대부분 앱에 도달하지만 캐시 사용 URL은 최초 MISS 정도만 앱에 도달한 것을 구분할 수 있다. `logs/tomcat/access`가 생기지 않으면 access log 설정이 적용되지 않은 것이므로 04-트러블슈팅을 따른다.

정상이라면 캐시 사용 요청의 전체 시간이 우회 요청보다 짧거나 비슷하고, **Tomcat 전달 횟수는 확실히 작아야 한다.** 로컬 PC에서는 시간 차이가 작을 수 있으므로 시간보다 `BYPASS 요청은 다수 전달, 캐시 URL은 최초 MISS 정도만 전달`이라는 로그 차이를 핵심 결과로 기록한다.

## 4. Nginx 앞단에서 요청 제한·보호하기

### 4-1. 요청 속도 제한과 429

> **이 단계에서 검사하는 것:** 짧은 시간에 많은 요청을 보내면 Nginx가 일부를 `429`로 거부하고, 거부된 요청은 app까지 전달하지 않는지 확인한다.

`nginx/conf.d/00-observability.conf`의 마지막에 클라이언트별 요청 속도를 기억할 영역을 추가한다.

**작업 화면: 터미널 B — 공통 설정 파일 열기**

```bash
# 요청 제한 기준을 추가하기 위해 Nginx 관찰 설정 파일을 연다.
nano nginx/conf.d/00-observability.conf
```

nano 화면의 맨 아래에 다음 설정을 추가하고 저장·종료한다.

```nginx
limit_req_zone $binary_remote_addr zone=per_ip_rate:10m rate=5r/s;
```

| 설정 이름 | 의미 |
| --- | --- |
| `limit_req_zone` | 클라이언트별 요청 속도를 기억할 공통 영역을 만든다. |
| `$binary_remote_addr` | 요청을 보낸 IP 주소를 기준으로 구분한다. |
| `zone=per_ip_rate:10m` | 영역 이름을 `per_ip_rate`, 메모리 크기를 10MB로 정한다. |
| `rate=5r/s` | IP 하나당 평균 초당 5개 요청을 기준으로 삼는다. |

`nginx/conf.d/default.conf`의 `server`에는 거절 상태와 로그 수준을, 일반 `location /`에는 실제 제한 규칙을 추가한다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# 실제 요청 경로에 요청 제한을 적용하기 위해 Nginx 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면에서 아래 주석에 표시된 두 위치에 각각 설정을 추가하고 저장·종료한다. `limit_req_status`와 `limit_req_log_level`은 **`server {` 시작 뒤, 첫 번째 `location`이 나오기 전**에 둔다. 정적 파일용 `location ~*` 안에 넣으면 일반 `/` 요청에는 적용되지 않는다.

```nginx
server {
  listen 80;
  access_log /dev/stdout study;

  # 여기에 추가: server 전체에 적용
  limit_req_status 429;
  limit_req_log_level notice;

  # 기존 정적 파일 location은 그대로 유지
  location ~* \.(?:css|js|png|jpe?g|gif|svg|ico)$ {
    # 기존 캐시 설정 ...
  }

  location / {
    # 기존 proxy 설정 ...

    # 여기에 추가: 일반 PetClinic 요청에 속도 제한 적용
    limit_req zone=per_ip_rate burst=10 nodelay;
  }
}
```

| 설정 이름 | 의미 |
| --- | --- |
| `limit_req_status 429` | 제한된 요청에 429 상태 코드를 반환한다. |
| `limit_req_log_level notice` | 제한 발생을 Nginx notice 로그에 남긴다. |
| `limit_req` | 일반 PetClinic 요청에 `per_ip_rate` 제한을 적용한다. |
| `burst=10` | 순간적으로 기준을 넘는 요청을 10개까지 추가로 허용한다. |
| `nodelay` | 허용된 burst 요청을 지연시키지 않고 바로 처리한다. |

**작업 화면: 터미널 B**

```bash
# 수정한 요청 제한 설정의 Nginx 문법이 올바른지 검사한다.
docker compose exec nginx nginx -t
# 문법 검사가 성공한 요청 제한 설정을 실행 중인 Nginx에 반영한다.
docker compose exec nginx nginx -s reload

# 요청 한 건은 제한되지 않고 200으로 처리되는지 먼저 확인한다.
curl -sS -o /dev/null -w '%{http_code}\n' \
  'http://localhost:8080/?study=step4-ok'

# 요청 50개를 최대 20개씩 동시에 보내 200과 429의 개수를 확인한다.
awk 'BEGIN {for(i=1;i<=50;i++) print i}' | xargs -P 20 -I{} sh -c \
  'curl -sS -o /dev/null -w "%{http_code}\n" "http://localhost:8080/?study=step4-rate"' | \
  sort | uniq -c

# 최근 Nginx 로그에서 요청 제한으로 거부된 429 요청만 찾는다.
docker compose logs --since 2m --no-log-prefix nginx | \
  grep -E 'rate_limit=REJECTED|status=429'

# 같은 시험 요청이 PetClinic까지 몇 건 전달됐는지 Tomcat 로그에서 센다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -h 'study=step4-rate' {} + | wc -l
```

| 명령 부분 | 의미 |
| --- | --- |
| `nginx -t`·`reload` | 설정을 검사한 뒤 실행 중인 Nginx에 반영한다. |
| 첫 번째 `curl` | 요청 한 건이 정상적으로 200인지 확인한다. |
| `awk ... 50` | 시험 요청 50개를 만든다. |
| `xargs -P 20` | 최대 20개 요청을 동시에 보낸다. |
| `sort | uniq -c` | 상태 코드별 응답 개수를 센다. |
| Nginx 로그 검색 | 제한된 `429`와 `REJECTED`를 찾는다. |
| Tomcat 로그의 `wc -l` | 50개 중 실제 app까지 전달된 수를 센다. |

정상 요청은 `200`, 병렬 요청 중 일부는 `429`가 기대값이다. Nginx 로그에는 거절된 요청이 보이지만 Tomcat에 기록된 요청 수는 전체 50개보다 적어야 한다. 즉, 허용된 요청만 app까지 전달된 것이다.

`sort | uniq -c` 결과는 환경마다 개수가 달라도 `200`과 `429`가 함께 나오면 정상이다. 예를 들면 `11 200`, `39 429`처럼 표시된다.

### 4-2. 요청 본문 크기 제한과 413

> **이 단계에서 검사하는 것:** 설정한 1KiB보다 큰 2KiB 요청 본문을 Nginx가 `413`으로 차단하고, Tomcat에는 같은 요청이 남지 않는지 확인한다.

`default.conf`의 `server`에 학습용 제한값을 추가한다. 위치는 **`server {` 시작 뒤, 첫 번째 `location`이 나오기 전**이다. 정적 파일용 `location ~*` 안에 넣으면 이미지·CSS 요청에만 적용되고 `/owners/new`에는 적용되지 않는다.

> 이미 `limit_req_status`, `limit_req_log_level`, `client_max_body_size`를 정적 파일용 `location ~* { ... }` 안에 넣었다면 그 자리에서는 삭제하고, 세 줄을 `access_log` 다음이면서 첫 번째 `location`보다 앞인 위치로 옮긴다. 같은 설정을 두 곳에 중복해서 남기지 않는다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# 요청 본문 크기 제한을 추가하기 위해 Nginx 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면에서 `access_log`와 4-1의 요청 제한 설정 다음, 첫 번째 `location`보다 앞에 추가하고 저장·종료한다.

```nginx
server {
  listen 80;
  access_log /dev/stdout study;

  limit_req_status 429;
  limit_req_log_level notice;
  client_max_body_size 1k;  # 여기에 추가

  location ~* \.(?:css|js|png|jpe?g|gif|svg|ico)$ {
    # 기존 정적 파일 캐시 설정 ...
  }

  location / {
    # 기존 proxy·요청 제한 설정 ...
  }
}
```

`client_max_body_size`는 사용자가 보내는 요청 본문의 최대 크기다. 여기서는 결과를 쉽게 보기 위해 1KiB로 낮춘다.

**① 설정이 파일과 실행 중인 Nginx에 모두 반영됐는지 확인**

**작업 화면: 터미널 B**

```bash
# 호스트 파일에서 1KB 제한과 주변 중괄호를 함께 확인해 server 범위인지 판정한다.
grep -n -C 10 'client_max_body_size' nginx/conf.d/default.conf

# 수정한 본문 크기 제한 설정의 Nginx 문법이 올바른지 검사한다.
docker compose exec nginx nginx -t
# 문법 검사가 성공한 본문 크기 제한 설정을 실행 중인 Nginx에 반영한다.
docker compose exec nginx nginx -s reload

# 실행 중인 Nginx에서도 설정과 주변 중괄호를 함께 확인해 server 범위인지 판정한다.
docker compose exec nginx nginx -T 2>&1 | \
  grep -n -C 10 'client_max_body_size'
```

두 검색 결과에 `client_max_body_size 1k;`가 보이고, 그 줄이 첫 번째 `location`보다 위에 있어야 다음 시험으로 넘어간다. 설정이 보여도 정적 파일용 `location ~* { ... }`의 닫는 `}`보다 위에 있다면 잘못된 범위이므로 2KB `/owners/new` 요청에는 적용되지 않는다.

- 첫 번째 검색에도 없음: `default.conf`에 설정을 추가하지 않았거나 nano에서 저장하지 않은 상태다.
- 첫 번째에는 있고 두 번째에는 없음: 실행 중인 Nginx가 수정 파일을 읽지 않은 상태다. Nginx 설정 마운트와 reload 결과를 확인한다.

**② 2KB 요청을 보내 413 재현**

**작업 화면: 같은 터미널 B**

```bash

# 요청 제한 시험의 임시 제한 상태가 풀릴 때까지 3초 기다린다.
sleep 3
# 이전 시험 로그와 섞이지 않도록 이번 본문 크기 시험의 고유 ID를 만든다.
BODY_TEST_ID="step4-body-$(date +%s)-$$"
# 2KB 본문을 POST로 보내 Nginx가 1KB 제한을 초과한 요청을 413으로 차단하는지 확인한다.
dd if=/dev/zero bs=2048 count=1 2>/dev/null | tr '\0' 'a' | \
  curl -sS -o /dev/null -w 'HTTP %{http_code}\n' -X POST --data-binary @- \
  "http://localhost:8080/owners/new?study=$BODY_TEST_ID"
```

정상이면 긴 HTML 화면 대신 `HTTP 413` 한 줄만 출력된다. `HTTP 200`이면 제한이 아직 적용되지 않은 것이므로 위 ①로 돌아간다.

**③ Nginx에서 차단되고 Tomcat에는 도달하지 않았는지 확인**

**작업 화면: 같은 터미널 B**

```bash

# 최근 Nginx 로그에서 해당 요청의 413 상태를 확인한다.
docker compose logs --since 1h --no-log-prefix nginx | \
  grep "study=$BODY_TEST_ID" | grep 'status=413'

# Tomcat 로그에 같은 요청이 없는지 확인해 Nginx 앞단에서 차단됐음을 검증한다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -h "study=$BODY_TEST_ID" {} + || true
```

| 명령 부분 | 의미 |
| --- | --- |
| 첫 번째 `grep` | 편집한 호스트 파일에서 설정의 존재와 중괄호 위치를 함께 확인한다. |
| `nginx -T` 뒤의 `grep` | 실행 중인 Nginx에서도 같은 설정이 `server` 범위에 있는지 확인한다. |
| `sleep 3` | 앞의 속도 제한 시험이 사용한 요청 여유가 회복되기를 잠시 기다린다. |
| `BODY_TEST_ID=...` | 이전에 실패한 시험 로그와 이번 재시험 로그가 섞이지 않게 한다. |
| `dd ... bs=2048 count=1` | 2KiB 크기의 시험 데이터를 만든다. |
| `tr` | 0으로 채워진 데이터를 문자 `a`로 바꾼다. |
| `curl --data-binary @-` | 앞 명령이 만든 2KiB 데이터를 POST 본문으로 보내고 상태코드만 출력한다. |
| Nginx 로그 검색 | 최종 상태가 413인지 확인한다. |
| Tomcat 로그 검색 | 차단된 요청이 app까지 가지 않았는지 확인한다. |

2 KiB 본문은 설정한 1 KiB보다 크므로 Nginx가 `413`을 반환한다. Tomcat 로그에는 같은 `BODY_TEST_ID` 요청이 없어야 한다.

터미널에 `HTTP 413`이 나오면 정상이다. 마지막 Tomcat 검색 명령은 **아무것도 출력하지 않는 것이 정상 결과**다.

### 4-3. 메서드·경로 차단

> **이 단계에서 검사하는 것:** 읽기 전용 경로의 GET은 허용하고 POST는 `405`, 비공개 경로는 `403`으로 Nginx가 직접 차단하는지 확인한다.

PetClinic의 실제 기능을 건드리지 않고 확인하도록 `default.conf`의 `server` 안에 Nginx 전용 연습 주소 두 개를 추가한다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# 학습용 메서드·비공개 경로 차단 규칙을 추가하기 위해 Nginx 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면의 `server {}` 안에 다음 두 `location`을 추가하고 저장·종료한다.

```nginx
location = /study/read-only {
  if ($request_method !~ ^(GET|HEAD)$) { return 405; }
  return 204;
}

location = /study/private {
  return 403;
}
```

| 설정 이름 | 의미 |
| --- | --- |
| `location =` | 주소가 정확히 일치하는 요청만 처리한다. |
| `$request_method` | 요청의 GET·POST 같은 HTTP 메서드를 뜻한다. |
| `return 405` | GET·HEAD 이외의 메서드를 허용하지 않는다고 응답한다. |
| `return 204` | 허용된 읽기 요청에는 본문 없이 성공으로 응답한다. |
| `return 403` | 학습용 비공개 경로의 접근을 거부한다. |

**작업 화면: 터미널 B**

```bash
# 수정한 메서드·경로 차단 설정의 Nginx 문법이 올바른지 검사한다.
docker compose exec nginx nginx -t
# 문법 검사가 성공한 메서드·경로 차단 설정을 실행 중인 Nginx에 반영한다.
docker compose exec nginx nginx -s reload

# 읽기 전용 학습 경로에 GET을 보내 본문 없는 정상 응답 204를 확인한다.
curl -i 'http://localhost:8080/study/read-only?study=step4-read'
# 같은 읽기 전용 경로에 POST를 보내 405로 차단되는지 확인한다.
curl -i -X POST --data 'study=true' \
  'http://localhost:8080/study/read-only?study=step4-method'
# 비공개 학습 경로에 요청해 Nginx가 403으로 차단하는지 확인한다.
curl -i 'http://localhost:8080/study/private?study=step4-private'

# Nginx 로그에서 GET 204·POST 405·비공개 403 요청을 함께 찾는다.
docker compose logs --since 2m --no-log-prefix nginx | \
  grep -E 'study=step4-(read|method|private)'

# Tomcat 로그에서 차단된 POST·비공개 요청이 app에 도달하지 않았는지 확인한다.
find logs/tomcat/access -type f -name 'access_log*.log' \
  -exec grep -hE 'study=step4-(read|method|private)' {} + || true
```

| 명령 | 확인하는 것 |
| --- | --- |
| 첫 번째 `curl` | GET 요청이 204로 허용되는지 확인한다. |
| 두 번째 `curl -X POST` | POST 요청이 405로 차단되는지 확인한다. |
| 세 번째 `curl` | 비공개 경로가 403인지 확인한다. |
| Nginx 로그 검색 | 세 요청과 각 상태 코드가 기록됐는지 확인한다. |
| Tomcat 로그 검색 | Nginx가 직접 처리해 app에는 전달하지 않았는지 확인한다. |

기대 결과는 `GET /study/read-only → 204`, `POST /study/read-only → 405`, `/study/private → 403`이다. 세 요청은 Nginx가 직접 처리하므로 Nginx 로그에는 남고 Tomcat 로그에는 없어야 한다.

세 `curl -i` 명령의 첫 줄을 차례대로 확인한다.

```text
HTTP/1.1 204 No Content
HTTP/1.1 405 Not Allowed
HTTP/1.1 403 Forbidden
```

마지막 Tomcat 검색 명령은 아무것도 출력하지 않아야 한다.

### 4-4. 버전 숨김과 보안 헤더

> **이 단계에서 검사하는 것:** 응답에서 Nginx 상세 버전이 숨겨지고, 일반 화면과 정적 파일에 기본 보안 헤더가 모두 붙는지 확인한다.

`default.conf`의 `server`에 버전 숨김과 일반 응답용 보안 헤더를 추가한다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# Nginx 버전 숨김과 보안 응답 헤더를 추가하기 위해 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면의 `server {}` 안에 다음 설정을 추가한다.

```nginx
server_tokens off;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

| 설정 이름 | 의미 |
| --- | --- |
| `server_tokens off` | 응답의 `Server` 헤더에서 구체적인 Nginx 버전 번호를 숨긴다. |
| `X-Content-Type-Options` | 브라우저가 파일 형식을 임의로 추측하지 않게 한다. |
| `X-Frame-Options` | 다른 사이트가 PetClinic 화면을 함부로 프레임에 넣는 것을 제한한다. |
| `Referrer-Policy` | 다른 사이트로 전달되는 현재 페이지 주소 정보를 줄인다. |
| `always` | 오류 응답에도 해당 헤더를 붙인다. |

3단계에서 만든 정적 파일 `location`에는 이미 `X-Cache-Status`가 있다. 상위 헤더가 빠지지 않도록 같은 보안 헤더 세 줄을 그 `location`에도 추가한다.

같은 nano 화면에서 정적 파일 `location` 안의 `add_header X-Cache-Status` 아래에도 다음 세 줄을 추가한 뒤 저장·종료한다.

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

**작업 화면: 터미널 B**

```bash
# 수정한 버전 숨김·보안 헤더 설정의 Nginx 문법이 올바른지 검사한다.
docker compose exec nginx nginx -t
# 문법 검사가 성공한 보안 설정을 실행 중인 Nginx에 반영한다.
docker compose exec nginx nginx -s reload

# IMAGE_PATH가 없으면 기본 PetClinic 이미지 경로를 사용한다.
IMAGE_PATH=${IMAGE_PATH:-resources/images/pets.png}
# 정적 파일의 캐시·보안 헤더를 시험할 전체 URL을 만든다.
ASSET="http://localhost:8080/$IMAGE_PATH?study=step4-static"

# 일반 PetClinic 화면에서 Nginx 버전과 세 보안 헤더를 확인한다.
curl -sS -D - -o /dev/null http://localhost:8080/ | \
  grep -iE '^(server|x-content-type-options|x-frame-options|referrer-policy):'

# 정적 이미지 응답에도 캐시 헤더와 세 보안 헤더가 모두 있는지 확인한다.
curl -sS -D - -o /dev/null "$ASSET" | \
  grep -iE '^(x-cache-status|x-content-type-options|x-frame-options|referrer-policy):'
```

| 명령 부분 | 의미 |
| --- | --- |
| `IMAGE_PATH=${IMAGE_PATH:-...}` | 앞에서 변수를 만들지 않았으면 기본 이미지 경로를 사용한다. |
| `curl -D - -o /dev/null` | 본문은 버리고 응답 헤더만 출력한다. |
| 첫 번째 `grep` | 일반 화면의 Server·보안 헤더를 확인한다. |
| 두 번째 `grep` | 정적 이미지의 캐시·보안 헤더를 확인한다. |

일반 응답의 `Server` 헤더에는 구체적인 Nginx 버전 번호가 없어야 한다. 일반 화면과 정적 이미지에는 보안 헤더 세 개가 모두 있어야 하며, 정적 이미지에는 `X-Cache-Status`도 함께 있어야 한다.

예상 출력은 `Server: nginx`처럼 버전 숫자가 없고, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`가 각각 한 줄씩 보이는 형태다.

### 4-5. 학습용 제한 설정 정리

> **이 단계에서 검사하는 것:** 결과를 쉽게 보기 위해 낮춘 요청 제한값을 제거하거나 팀 기준으로 되돌리고, 일반 PetClinic 사용이 다시 정상인지 확인한다.

`rate=5r/s`와 `client_max_body_size 1k`는 결과를 쉽게 확인하기 위한 값이다. 5단계로 넘어가기 전에 다음처럼 정리한다.

#### 4-5-1. `00-observability.conf` 전체 내용으로 교체

요청 속도 제한 시험이 끝났으므로 `limit_req_zone`을 제거한다. 로그 형식과 캐시 저장소는 이후에도 사용하므로 그대로 남긴다.

**작업 화면: 터미널 B — 관찰 설정 파일 열기**

```bash
# 학습용 요청 제한 기준을 제거한 최종 내용으로 교체하기 위해 관찰 설정 파일을 연다.
nano nginx/conf.d/00-observability.conf
```

nano 화면의 기존 내용을 모두 지우고 아래 전체 내용을 붙여 넣은 뒤 `Ctrl+O → Enter → Ctrl+X`로 저장·종료한다.

```nginx
log_format study 'time=$time_iso8601 status=$status method=$request_method '
                 'uri="$request_uri" cache=$upstream_cache_status '
                 'rate_limit=$limit_req_status request_time=$request_time '
                 'upstream_time=$upstream_response_time upstream="$upstream_addr"';
error_log /dev/stderr notice;

proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=petclinic_cache:10m
                 inactive=10m max_size=100m use_temp_path=off;
```

이 최종 내용에는 `limit_req_zone`이 없다. `log_format`과 `proxy_cache_path`는 삭제하지 않는다.

#### 4-5-2. `default.conf` 전체 내용으로 교체

요청 속도 제한 설정과 연습용 차단 경로는 제거하고, 본문 크기 제한은 일반적인 `1m`으로 되돌린다. 캐시·버전 숨김·보안 헤더·리버스 프록시는 유지한다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# 학습용 제한을 정리한 최종 내용으로 교체하기 위해 Nginx 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면의 기존 내용을 모두 지우고 아래 전체 내용을 붙여 넣은 뒤 `Ctrl+O → Enter → Ctrl+X`로 저장·종료한다.

```nginx
server {
  listen 80;
  access_log /dev/stdout study;

  server_tokens off;
  client_max_body_size 1m;

  add_header X-Content-Type-Options "nosniff" always;
  add_header X-Frame-Options "SAMEORIGIN" always;
  add_header Referrer-Policy "strict-origin-when-cross-origin" always;

  location ~* \.(?:css|js|png|jpe?g|gif|svg|ico)$ {
    proxy_pass http://app:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_cache petclinic_cache;
    proxy_cache_valid 200 5m;
    proxy_cache_methods GET HEAD;
    proxy_cache_bypass $arg_bypass_cache;
    proxy_no_cache $arg_bypass_cache;

    add_header X-Cache-Status $upstream_cache_status always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
  }

  location / {
    proxy_pass http://app:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

| 최종 상태 | 정리하는 이유 |
| --- | --- |
| `client_max_body_size 1m` | 1KiB 제한 때문에 정상 폼 요청까지 막히는 것을 방지한다. |
| 요청 속도 제한 설정 없음 | 학습용 초당 5회 제한을 종료한다. |
| `/study/read-only`·`/study/private` 없음 | 시험용으로 만든 가상 경로를 제거한다. |
| 캐시·버전 숨김·보안 헤더 유지 | 다음 장애 실습과 일반 PetClinic 사용에서도 계속 적용한다. |

#### 4-5-3. 두 파일 검사·반영

**작업 화면: 터미널 B**

```bash
# 제한값을 정리한 뒤 Nginx 설정 문법이 올바른지 검사한다.
docker compose exec nginx nginx -t
# 문법 검사가 성공한 정리 설정을 실행 중인 Nginx에 반영한다.
docker compose exec nginx nginx -s reload
```

`nginx -t`로 정리 후 문법을 검사하고, 성공했을 때만 `reload`로 반영한다. 이 단계에서는 새 기능을 시험하는 것이 아니라 학습용으로 낮춘 제한값 때문에 이후 PetClinic 사용이 막히지 않도록 원래 수준으로 되돌린다.

`nginx -t`에 `test is successful`이 나오고 reload 명령이 오류 없이 끝나면 정리가 적용된 것이다. PC 브라우저에서 PetClinic 첫 화면도 다시 열리는지 확인한다. `/study/read-only`와 `/study/private`는 제거했으므로 이후에는 기존의 `204·405·403` 결과가 나오지 않아도 정상이다.

## 5. PetClinic 장애 확인·안내·복구

### 5-1. 확인할 장애 상황

> **이 단계에서 검사하는 것:** app이 중지됐을 때도 Nginx는 살아 있지만 전달 대상이 없어 `502`가 발생한다는 장애 흐름과 성공 기준을 먼저 확인한다.

이번에는 Nginx는 실행한 채 `app`만 멈춘다. Nginx access log의 `502`로 사용자가 받은 결과를 확인하고, error log의 upstream 연결 오류로 원인을 확인한다.

```text
브라우저 → Nginx: 연결 성공
Nginx → app:8080: 연결 실패
브라우저 ← Nginx: 502 Bad Gateway
```

### 5-2. 사용자에게 보여 줄 오류 페이지 준비

> **이 단계에서 검사하는 것:** app 장애 시 HTTP 상태는 `502`로 유지하면서 기본 오류 화면 대신 이해하기 쉬운 안내 화면을 Nginx가 보여 주도록 준비한다.

Compose의 `nginx.volumes`에 오류 페이지 마운트를 추가한다.

**작업 화면: 터미널 B — Compose 파일 열기**

```bash
# Nginx에 사용자 안내용 오류 HTML을 연결하기 위해 Compose 파일을 연다.
nano docker-compose.yml
```

nano 화면에서 `services.nginx.volumes` 아래에 다음 한 줄을 추가하고 저장·종료한다.

```yaml
- ./nginx/html:/usr/share/nginx/html:ro
```

| 설정 부분 | 의미 |
| --- | --- |
| `./nginx/html` | PetClinic 폴더에서 우리가 오류 HTML을 저장할 위치다. |
| `/usr/share/nginx/html` | Nginx 컨테이너가 HTML 파일을 읽을 위치다. |
| `ro` | 컨테이너에서는 이 폴더를 수정하지 못하고 읽기만 하게 한다. |

호스트의 `nginx/html` 폴더 전체를 Nginx 컨테이너의 HTML 폴더에 읽기 전용으로 연결하는 설정이다. 폴더를 만들고 새 파일 `nginx/html/study-50x.html`을 작성한다.

**먼저 터미널 B에서 폴더 생성**

```bash
# 사용자 안내용 50x 오류 HTML을 보관할 폴더를 만든다.
mkdir -p nginx/html
```

`mkdir -p`는 `nginx/html` 폴더를 만들며, 이미 있어도 오류를 내지 않는다. 성공하면 별도 출력이 없다.

이 HTML은 독립된 새 파일이므로 아래 전체 내용을 작성한다.

**그다음 터미널 B에서 새 HTML 파일을 nano로 열기**

```bash
# app 장애 때 보여 줄 사용자 안내 HTML 파일을 새로 작성한다.
nano nginx/html/study-50x.html
```

nano 화면에 아래 전체 내용을 입력하고 저장·종료한다.

```html
<!doctype html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>PetClinic 연결 대기</title>
  <style>
    body { margin: 0; background: #f5f7fb; color: #172033; font-family: sans-serif; }
    main { max-width: 640px; margin: 12vh auto; padding: 40px; background: white;
           border: 1px solid #d8deea; border-radius: 16px; }
    h1 { color: #1f5ea8; }
  </style>
</head>
<body>
  <main>
    <h1>잠시 PetClinic에 연결할 수 없습니다</h1>
    <p>Nginx는 정상 동작 중이지만 뒤쪽 애플리케이션이 응답하지 않습니다.</p>
    <p>잠시 후 다시 시도해 주세요.</p>
  </main>
</body>
</html>
```

`default.conf`의 `server` 안에 오류 페이지 연결을 추가하고, 일반 `location /` 안에는 `proxy_intercept_errors on;`을 추가한다.

**작업 화면: 터미널 B — 웹 서버 설정 파일 열기**

```bash
# 같은 오류 페이지 설정을 이미 추가한 적이 있는지 먼저 찾아 중복을 막는다.
grep -n -C 2 -E 'proxy_intercept_errors|error_page|study-50x' nginx/conf.d/default.conf || true

# 502·503·504 발생 시 안내 HTML을 사용하도록 Nginx 웹 서버 설정 파일을 연다.
nano nginx/conf.d/default.conf
```

nano 화면에서 `server {}`와 기존 `location /`의 안내된 위치에 다음 설정을 추가하고 저장·종료한다. 이전에 같은 실습을 시도한 적이 있다면 새 줄을 또 추가하지 말고, 각 설정을 **정확히 한 번씩만** 남긴다. 특히 `proxy_intercept_errors on;`은 `location / { ... }` 안에 한 줄만 둔다.

```nginx
error_page 502 503 504 /study-50x.html;

location = /study-50x.html {
  root /usr/share/nginx/html;
  internal;
}

# 기존 location / 안에 추가
proxy_intercept_errors on;
```

| 설정 이름 | 의미 |
| --- | --- |
| `error_page 502 503 504` | 세 서버 오류가 발생하면 작성한 HTML을 사용한다. |
| `location = /study-50x.html` | 오류 HTML을 읽을 정확한 내부 경로를 만든다. |
| `root` | 오류 HTML 파일이 있는 컨테이너 폴더를 지정한다. |
| `internal` | 사용자가 HTML 주소를 직접 열지 못하고 오류 처리 중에만 사용하게 한다. |
| `proxy_intercept_errors` | app에서 받은 5xx 응답도 Nginx가 오류 페이지로 바꿔 보여 주게 한다. |

Compose 마운트가 바뀌었으므로 새 정의로 검사하고 Nginx 컨테이너를 재생성한다.

**작업 화면: 터미널 B**

```bash
# 새 HTML 마운트까지 포함한 Nginx 설정을 임시 컨테이너에서 검사한다.
docker compose run --rm --no-deps nginx nginx -t
# Compose의 새 HTML 볼륨 연결을 적용하도록 Nginx 컨테이너를 다시 만든다.
docker compose up -d --force-recreate nginx
# internal 오류 페이지를 사용자가 주소로 직접 열 수 없는지 404 응답으로 확인한다.
curl -i http://localhost:8080/study-50x.html
```

| 명령 | 의미 |
| --- | --- |
| `docker compose run ... nginx -t` | 새 HTML 마운트를 포함한 임시 컨테이너에서 Nginx 문법을 검사한다. |
| `up -d --force-recreate nginx` | Compose의 새 볼륨 연결을 적용하도록 Nginx 컨테이너를 다시 만든다. |
| `curl .../study-50x.html` | 사용자가 내부 오류 파일을 직접 열 수 없는지 확인한다. |

마지막 직접 요청은 `internal` 설정 때문에 `404`가 기대값이다. 이 파일은 사용자가 주소로 직접 여는 페이지가 아니라 실제 5xx 오류가 발생했을 때 Nginx가 내부적으로 사용하는 페이지다.

`nginx -t`에는 `test is successful`이 나오고, 마지막 `curl -i`의 첫 줄은 `HTTP/1.1 404 Not Found`여야 한다. `404`는 오류 페이지 파일이 없다는 뜻이 아니라 사용자가 파일 주소를 직접 여는 것을 막았다는 뜻이다.

### 5-3. app 중지와 복구 판정

> **이 단계에서 검사하는 것:** app 중지→502와 연결 실패 로그→app 재시작→200 복구의 전체 과정을 상태코드와 로그로 확인한다.

**작업 화면: 터미널 B — 장애 발생과 원인 확인**

```bash
# 장애 상황을 재현하기 위해 PetClinic app 컨테이너만 중지한다.
docker compose stop app
# Nginx에 요청해 상태는 502이면서 사용자 안내 화면이 표시되는지 확인한다.
curl --max-time 20 -i 'http://localhost:8080/?study=step5-down'
# Nginx access log에서 방금 장애 요청의 502 상태를 확인한다.
docker compose logs --since 1m --no-log-prefix nginx | \
  grep 'study=step5-down' | grep 'status=502'
# Nginx error log에서 app 연결 실패 원인을 나타내는 문구를 찾는다.
docker compose logs --since 1m --no-log-prefix nginx | \
  grep -Ei 'connect\(\) failed|no live upstreams|upstream timed out|host not found in upstream'

# 장애 시험이 끝난 PetClinic app 컨테이너를 다시 시작한다.
docker compose start app
```

| 명령 | 의미 |
| --- | --- |
| `stop app` | Nginx·PostgreSQL은 유지하고 PetClinic 컨테이너만 멈춘다. |
| `curl --max-time 20 -i` | 최대 20초 기다리며 사용자에게 반환되는 상태와 안내 HTML을 확인한다. |
| 첫 번째 로그 검색 | access log에서 사용자가 받은 `502`를 확인한다. |
| 두 번째 로그 검색 | error log에서 app 연결 실패 원인을 확인한다. |
| `start app` | 중지했던 PetClinic 컨테이너를 다시 시작한다. |

**작업 화면: 터미널 A — 재시작한 app 로그 관찰**

```bash
# 재시작한 app이 Started 상태까지 정상 복구되는지 실시간으로 확인한다.
docker compose logs -f --since 10s app
```

`logs -f`는 재시작 직후 app 로그를 계속 보여 준다. `Started ...`가 나타날 때까지 기다린다.

`Started ...`가 보이면 app 기동이 완료된 것이다. 터미널 A는 그대로 두거나 `Ctrl+C`로 로그 보기만 끝낸다.

**작업 화면: 터미널 B — 복구 결과 확인**

```bash
# app 복구 후 Nginx 요청이 다시 200으로 처리되는지 확인한다.
curl -i 'http://localhost:8080/?study=step5-up'
# 장애 때의 502와 복구 후 200을 Nginx 로그에서 함께 비교한다.
docker compose logs --since 2m --no-log-prefix nginx | \
  grep -E 'study=step5-(down|up)'
```

첫 명령은 복구된 PetClinic이 다시 `200`을 반환하는지 확인한다. 두 번째 명령은 같은 로그에서 장애 요청 `down`과 복구 요청 `up`을 함께 찾아 `502 → 200` 변화를 비교한다.

app을 멈춘 뒤 브라우저에서 `http://localhost:8080/?study=step5-down`도 연다. 기본 502 화면 대신 작성한 안내 화면이 보이지만 `curl -i`의 상태 줄은 여전히 `502`여야 한다. 화면 내용만 바꾸고 장애 상태 코드는 유지한 것이다.

즉, 두 화면에서 다음을 확인한다.

- Ubuntu 터미널: `HTTP/1.1 502 Bad Gateway`
- PC 브라우저: 밝은 배경의 “잠시 PetClinic에 연결할 수 없습니다” 안내 화면

Nginx access log의 `status=502`, error log의 `connect() failed` 또는 upstream 오류가 한 묶음으로 보여야 한다. app 재시작 뒤 다음 세 가지가 모두 확인되면 복구다.

1. app 로그에 Spring의 `Started ...`가 보인다.
2. `study=step5-up` 요청이 `200`을 반환한다.
3. Nginx access log에 app upstream 주소가 다시 보인다.

다른 앱으로 자동 우회하는 로드밸런싱은 5주차 범위다.

app 로그에 `relation ... already exists`가 나오며 다시 종료되면 프록시 문제가 아니라 초기화 SQL 재실행 문제다. 3주차 DB 테이블이 존재하는지 확인하고 app 환경 변수의 `SPRING_SQL_INIT_MODE=never`를 확인한 뒤 app 컨테이너를 재생성한다. DB 볼륨은 삭제하지 않는다.

여기서는 로그 종류를 구분해야 한다. access log는 사용자가 받은 최종 결과 `502`를 보여 주고, error log는 `app:8080` 연결 실패라는 원인을 보여 준다. 복구 후에는 새 `/` 요청의 access log가 `200`이고 upstream 값이 다시 생기는지 확인한다.

## 종료

**작업 화면: 터미널 B**

```bash
# 실습 컨테이너와 네트워크를 종료하되 PostgreSQL 데이터 볼륨은 보존한다.
docker compose down
```

`-v`를 붙이지 않는다. 그러면 PostgreSQL Named Volume을 보존한 채 컨테이너만 내린다.

정상이라면 컨테이너가 `Stopped`, `Removed`되는 문구가 나오고, `docker compose ps`를 다시 실행했을 때 실행 중인 4주차 서비스가 보이지 않는다. 데이터 볼륨은 유지되므로 다음 실행 때 기존 데이터가 다시 연결된다.

| 최종 확인 | 성공 기준 |
| --- | --- |
| 1. 연결 | 세 서비스 실행, `nginx -t` 성공, Nginx 경유 응답 |
| 2. 비공개 | Nginx만 게시되고 app·postgres는 내부 네트워크에서 실행 |
| 3. 캐시 | 실제 이미지에서 `MISS → HIT`, 시간과 app 전달 횟수 감소 |
| 4. 보호 | `429/413/405/403` 및 보안 헤더를 각각 확인 |
| 5. 장애 | 안내 화면과 HTTP `502`, 원인 로그, app 재시작 후 정상 복구 |
